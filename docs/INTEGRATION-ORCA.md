# Orca 深度绑定方案（补充设计 · 待评审）

**日期**：2026-10-18
**关联文档**：`PRODUCT-DESIGN-v0.1.md`
**结论先说**：Orca 应当被绑成**执行面的一个 Runtime Provider**，不是控制面，也不是第二套看板。绑定深度建议做到 **L2（会话级）**，L3（组织级）留到 v0.9。但有三条硬约束会改变容量模型和成本口径，必须先认。

---

## 1. 先把两者的位置摆正

对 Orca 仓库的核对结论（截至 2026-10-18，MIT，约 1.5 万次提交）：

| 维度 | Orca 是什么 |
|---|---|
| 定位 | **CLI 编码 Agent 的编排工作台**（Electron 桌面端 + 移动伴侣 + 远程运行时） |
| 自带 Agent 吗 | ❌ 不带。BYO Agent——Claude Code / Codex / OpenCode / Pi 都行，用的是**你自己的订阅** |
| 隔离单位 | **git worktree**（`repo.id::path`），一个 Agent 一个 worktree |
| 会话单位 | **PTY / terminal split**，有持久终端守护进程 |
| 对外接口 | **CLI 为主**（`orca worktree`、`snapshot`、`click`、`fill`、`linear` 等）；README **未声明** 公开 HTTP API / SDK / MCP；内部走 cloud relay |
| 生命周期钩子 | 有 `agent-hooks`（sidebar 排序依赖 hook rows） |
| 额外能力 | Computer Use、Design Mode（点选真实 Chromium 元素取 HTML/CSS/截图）、GitHub/Linear/Jira 集成、移动端 steer |

**所以分工是一句话**：

> **Orca 管"一个任务怎么被做完"，我们管"哪些任务值得做、预算够不够、做完算不算数"。**

**由此得到三条设计纪律**：

1. **不要在 Orca 之上再建一套舰队看板。** 终端、分屏、steering、PR 浏览都交给 Orca，我们只在"目标/预算/质量/闸门"这四个维度上加视图。重复建设是这套整合最容易犯的错。
2. **不要把 Orca 当 API 用。** 它没有稳定 HTTP 契约，只有 CLI 和 GUI。绑定必须建在"CLI + 文件系统 + hooks"这三个事实上，而且要假设 CLI 会变（日均多次提交）。
3. **不要把业务逻辑写进 Orca。** 目标、预算、验收标准必须留在我们这边，Orca 侧只留一份"这个 worktree 属于哪个任务"的声明文件。

## 2. 能力核对：谁补谁的缺口

| 能力 | Orca | 我们 | 结论 |
|---|---|---|---|
| 任务执行、终端、文件隔离 | ✅ 强 | ❌ | 全交给 Orca |
| 多 Agent 并行扇出 | ✅ 强 | ⚠️ 弱 | 交给 Orca（我们只下发 DAG 节点） |
| 移动端监控与 steer | ✅ | ❌ | 直接复用，等于白送一个"远程闸门" |
| Computer Use / 浏览器点选 | ✅ | ❌ | 复用 |
| 目标与预算 | ❌ | ✅ | 我们 |
| 成本归因（CPO） | ❌ | ✅ | 我们（但口径要改，见第 6 节） |
| 质量验收与效果评估 | ❌ | ✅ | 我们 |
| 人工闸门与审计 | ⚠️ 有 steer，无审批流 | ✅ | 我们（但可复用它的 UI 做入口） |
| 能力注册表 / Provider 比价 | ❌ | ✅ | 我们 |
| 跨主机的 Agent 池与退役 | ⚠️ 弱（单机为主） | ✅ | 我们 |
| 技能分发 | ✅ 有 `skills/` 目录 | ✅ 我们做真相源 | 我们发版，它执行（见 4.5） |

> 一句话：**Orca 是"手和眼睛"，我们是"脑和账本"。** 唯一重叠的是"舰队视图"，必须让给它。

## 3. 绑定深度分级（建议选 L2）

| 级别 | 绑什么 | 我们的改造成本 | 得到什么 | 风险 |
|---|---|---|---|---|
| **L1 任务级**（最松） | Adapter 调 CLI 建 worktree、起会话、塞 prompt、收结果 | 3–5 人日 | 能把 Orca 当 Worker 用，任务不重不漏 | 只能拿到最终产物，看不到过程 |
| **L2 会话级**（建议） | + 会话即租约、hook 即心跳、transcript 即 trace、snapshot 断点续跑 | 8–12 人日 | 可中断/可续跑/可归因；成本能算到步骤 | CLI 面变化要跟进 |
| **L3 组织级**（暂缓） | + Agent 池跨主机、技能下发、闸门嵌进 Orca UI、订阅配额调度 | 20+ 人日 | 真正的"500 个工位" | 强耦合，CLI 一变全线返工 |

**为什么不是 L3**：L3 会把我们和 Orca 的内部实现（Electron IPC、relay、hook 字段）绑死，而它日均多次提交。按我上一轮评审里"能力直连上游"的反模式，这正是要避免的。**做法是：接口做浅，语义做深**——只依赖 4 个稳定事实（CLI 命令存在、worktree 在磁盘上、会话有 PTY、hook 能回调），其余全部走我们自己的协议。

## 4. 五个深度绑定机制（这是"深度"的全部含义）

### 4.1 会话即租约（核心）

```
我们派任务 → Adapter 在目标主机执行 orca worktree create → 得到 worktree 路径
          → 在 worktree 内起 CLI agent 会话（PTY）→ 把 session_id 写回 task 行
          → 租约 TTL 与"会话存活"绑定：session 活着 = 租约续期；session 死 = 租约到期
```

- 租约不再是"90 秒后不管了"，而是**由会话存活信号驱动**：hook 或 transcript 有增量就续租，静默超过 `3×心跳` 才判定为僵死。
- 好处：长任务（跑测试 20 分钟）不会被误回收；真挂掉的会话能在 1 个心跳内被发现。
- 这是 L1 与 L2 的分水岭：L1 只能靠超时猜，L2 能靠信号知道。

### 4.2 worktree 即任务载体

在每个 worktree 根目录写一个 `.fleet-task.json`：

```json
{
  "task_id": "T-20261018-0412",
  "objective_id": "O-20261018-007",
  "capability": "code.build.feature@v3",
  "skill_versions": {"web-scaffold": "1.4.2"},
  "prompt_ver": "2026-10-17.a",
  "budget_remaining": 0.82,
  "acceptance": {"cmd": "pnpm test && pnpm lint", "must_pass": true},
  "idem_key": "sha1:..."
}
```

为什么放磁盘而不是只放数据库：**任务在中断后能自解释**。任何一台机器捡到这个 worktree，读这个文件就知道该干什么、验收标准是什么、预算还剩多少。这也是幂等的基础——`idem_key` 与 worktree 路径一一对应，重派不会产生第二个 worktree。

### 4.3 hook 即心跳

Orca 有 `agent-hooks` 生命周期钩子。Adapter 注册三类回调：

| 事件 | 我们做什么 |
|---|---|
| session 启动 | 记 `started_at`，开始计租约，写 trace 首条 span |
| 步骤/工具调用 | 续租 + 追加 span（这一步是"步骤级成本归因"的数据来源） |
| session 结束 | 触发 harvest（收 diff、收成本、收日志），任务进质检 |

> 若 hook 字段不足以覆盖（很可能，因为它是为 sidebar 排序设计的），退化方案是**监听 transcript 文件增量**（`ORCA_USER_DATA_PATH` 下），解析最后 N 行判断进度。两条路都走不通才退回纯超时。

### 4.4 transcript 即 trace

我们的 trace 不自己造，直接吸收会话记录：

```
trace_id = task_id
span = 一次工具调用 / 一次模型回合
字段 = {节点, 模型, prompt 版本, skill 版本, token, 成本, 耗时, 判定}
```

这样 3.3 那张"步骤级价值归因表"（哪一步贡献了多少质量、花了多少钱）才有数据可填——**这张表是全文所有降本结论的地基，而它只能从 transcript 长出来**。

### 4.5 snapshot 即断点续跑 + skill 分发

- **续跑**：Orca 有 `snapshot`。任务失败或租约回收时，先 snapshot，重派时从 snapshot 恢复，而不是从零重跑。对 20 分钟级的构建任务，这一条能把返工成本砍掉一半以上。
- **skill 分发**：Orca 有 `skills/`、`skill-guides/`、`skill-stubs/` 目录。我们的 skill 注册表作为**唯一真相源**，按主机下发到该目录（rsync 或 git submodule），版本号写进 `.fleet-task.json`。执行完从 transcript 回读版本号，形成"我们发版 → Orca 执行 → 版本可追溯"的闭环。

**顺带一个收益**：coding 场景有**真正的 oracle**（测试通过/不通过）。这意味着我在上一轮评审里限定"只在可自动验证的任务上用抢模式"——在 Orca 场景下**抢模式是成立的**：2–3 个 Agent 各自在自己的 worktree 里做同一个任务，跑同一套测试，取先通过且 diff 最小的。这是内容类业务做不到的。

## 5. Adapter 的六个动作（接口草案）

只做六个原子动作，任何 Orca 版本变化都只影响这六个函数的内部实现：

| 动作 | 输入 | 输出 | 失败语义 |
|---|---|---|---|
| `probe()` | — | 版本号、可用子命令、hooks 配置方式 | 版本不匹配 → 拒绝派活（不降级猜测） |
| `spawn(task)` | 任务、repo、branch 基点、snapshot | worktree 路径、session_id | 建目录失败 → 可重试 |
| `send(session, prompt)` | prompt、上下文文件 | 受理确认 | 会话不存在 → 重派（幂等键去重） |
| `steer(session, msg)` | 人的干预指令 | — | 用于闸门/纠偏 |
| `harvest(session)` | — | diff、日志、测试结果、token/成本、步骤 span | 无产物 → 判定失败 |
| `kill(session, mode)` | graceful/hard | — | 优雅停：先 snapshot 再杀 |

**验收信号怎么来**：coding 任务用 `.fleet-task.json` 里的 `acceptance.cmd` 在 harvest 阶段执行，退出码即结论；同时读 PR 状态（Orca 有 GitHub 集成）——**merge = 通过，reject = 返工**。这比让模型自评可靠一个数量级。

## 6. 必须跟着改的三件事（这是本轮最重要的部分）

### 6.1 成本口径要换：订阅制下边际成本 ≈ 0

Orca 的核心卖点是"用你自己的订阅，不买 API"。这会**打穿**我们原来的 CPO 模型——如果每个任务不产生增量费用，"模型成本"这一项会变成 0，CPO 看起来无限好，但这是假的。

真实稀缺资源变成三样：

| 原来的稀缺资源 | 现在的稀缺资源 | 新指标 |
|---|---|---|
| token 钱 | **订阅配额 / 速率限制** | 配额消耗率（已用 / 周期额度）、限流命中率 |
| 模型档位 | **并发会话位** | 会话位利用率、排队等待 P95 |
| — | **人类复核分钟数** | 每产出的复核分钟（min/outcome） |

**CPO 重定义为**：

```
CPO = (订阅摊销 + 工具 + 设备 + 返工 + 质检 + 人力) ÷ T+7 达标产出
```

订阅摊销 = 每账号月费 ÷ 该账号当月达标产出，而不是按 token 摊。**这个口径会立刻暴露一个真相：如果配额用不完，多买订阅是浪费；如果用完了在排队，订阅数就是硬瓶颈。**

### 6.2 容量单位要从"Agent 数"改成"并发会话数"

Orca 的容量单位是 **session / PTY**，不是 agent。一个 Electron 实例 + 若干 PTY 的实测内存与 CPU 是硬约束（需压测确认，粗略量级）：

| 主机 | 估计可承载并发会话 | 说明 |
|---|---|---|
| Mac mini 16GB | 8–12 | 每个会话含 node 进程 + 终端 + 可能的浏览器 |
| Linux 容器 8C16G | 10–15 | 无 GUI，Computer Use 不可用 |
| 高配工作站 64GB | 30–40 | 有 GUI 时上限更低 |

于是规模换算变成：**500 个 Agent ≠ 500 个会话**。若日活 60%、单会话平均占用 25% 时间，实际并发 ≈ 500 × 0.6 × 0.25 ≈ **75 个并发会话** → 约 **8–10 台主机**。这个数字比"500 台设备"现实得多，也说明**扩容决策要看队列等待 P95，而不是看 Agent 总数**。

> 这条直接修正了原设计里"设备 15–25 台"的估算逻辑：那是按账号数推的，不是按并发会话推的。

### 6.3 订阅条款是红线，不是成本项

"用一份订阅驱动 N 个 Agent"在多数厂商条款下**很可能不成立**（账号共享 / 自动化滥用 / 并发限制）。500 个 Agent 的规模下，这不是"技术能不能跑通"，而是"会不会被封 + 有没有法律风险"。

**建议**：
- POC 阶段就用**单账号单并发**验证，不做并发堆叠；
- 生产环境按"一个订阅 = 一个身份 = 一个审计边界"设计，不共享；
- 超过 20 个 Agent 后改用 API 计费或企业协议，把这笔钱算进模型成本——**这会推翻 6.1 的"边际成本≈0"，但不改流程，只改账**；
- 把"条款合规"列进闸门的高风险类目，人审。

## 7. 风险清单

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| CLI 面不稳定（日均多次提交） | 高 | 中 | `probe()` 启动自检 + 契约测试（每周跑一次六个动作）+ 版本白名单，不匹配就拒绝派活而非试错 |
| Electron 依赖 GUI / 显示环境 | 高 | 高 | 服务器版必须走无头或远程 host；Computer Use 类任务独占有 GUI 的主机 |
| 订阅条款/封号 | 中 | 极高 | 见 6.3；单账号单并发；合规进闸门 |
| 并发会话打满内存 | 中 | 高 | 会话池上限 + 排队 + 内存水位熔断（>85% 停止派活） |
| worktree 与 git 冲突（同一 repo 多 worktree） | 中 | 中 | 一任务一分支一 worktree；回收时强制清理；定期 `worktree prune` |
| 深度绑定导致迁移成本 | 中 | 中 | 六个动作 + 磁盘声明文件，是所有耦合的全部；换掉 Orca 只需重写 Adapter |
| hook 字段不够用 | 高 | 中 | transcript 监听兜底；再不行退回超时（功能降级不阻断） |

## 8. POC 三步（每步都可独立叫停）

| 步骤 | 做什么 | 工期 | 通过标准 |
|---|---|---|---|
| **P1 探测** | 只跑 `probe()`：枚举 CLI 子命令、hook 配置方式、worktree 实际路径、snapshot 行为 | 1 天 | 六个动作中至少 5 个有可用实现路径；否则调低绑定级别 |
| **P2 端到端** | 1 个任务：立目标 → 建 worktree → 起会话 → 跑测试 → harvest → 计入 CPO | 2–3 天 | 全链路可追溯；杀掉会话后能靠 snapshot 续跑 |
| **P3 压测** | 单主机并发阶梯：4 → 8 → 16 会话 | 2 天 | 找到内存/CPU 拐点，得出"每主机可承载会话数"；排队 P95 < 10min |

**P3 的产出会直接改写原方案的容量测算**——这是这套整合最值钱的一次测量。
