## 1. 问题定义：为什么现有的东西不够用

你现在的管理方式是"人去盯 Agent"。这套方式在 20 个 Agent 时成立，在 200 个时崩溃，原因不是能力不够，是**三个看不见**：

| 看不见 | 具体表现 | 后果 |
|---|---|---|
| **看不见钱花在哪** | 只有 API 账单，没有"每个有效产出花了多少" | 知道贵，不知道该砍哪一步 |
| **看不见谁在拖后腿** | 500 个 Agent 混在一起，失败率是个平均数 | 坏 Agent 被好 Agent 平均掉 |
| **看不见事情做到哪** | 派出去的任务没有状态，靠 Agent 自己汇报 | 重复发布、僵尸任务、交付黑洞 |

产品的全部价值，就是把这"三个看不见"变成三张可下钻的表。

**不解决的问题（明确排除）**：
- 不做 Agent 的推理框架（那是 WorkBuddy / Trae / Opencode 的事）
- 不做内容生成（只做"谁生成、生成得对不对、值不值"）
- 不做账号代运营工具（只做账号资产的登记与健康度）

## 2. 用户与使用场景

### 2.1 用户

| 角色 | 人数 | 每天在这套系统里做什么 | 停留时长 |
|---|---|---|---|
| **指挥官**（你） | 1 | 看总览、立项/砍目标、审高风险闸门、周复盘 | 30–60 min/日 |
| **运营官** | 1 | 审中低风险闸门、处理死信、维护合规规则、跟进目标进度 | 2–3 h/日 |
| **工程师** | 0.5–1 | 接 Worker、修 Provider、跑评估、发布 skill | 按需 |
| **机器初审**（系统内） | — | 对所有产出做规则 + 模型初筛，把 95% 的干净活挡在人之外 | 7×24 |

> 关键设计前提：**人的注意力是系统里最稀缺的资源。** 所有界面设计的唯一目标是"让人每天只处理 8–15 个决策"。

### 2.2 一天的动线（这是首页的设计依据）

```
07:50  夜间批处理收尾：状态快照、成本结算、次日任务预生成
08:00  系统推送《晨报》到微信/邮件：昨日吞吐、异常 3 条、今日待批 8 条
09:00  指挥官打开「今日」页 → 3 分钟看完 8 个指标 → 处理 3 个异常
09:15  进「闸门」页 → 机器已初审，人只做 8 个决策（约 6 分钟）
10:00  进「目标」页 → 立项 2 个（1 个下发 + 1 个机会雷达提案）
全天   系统自动跑；人只在"升级请求"到达时介入（目标 ≤8 次/日）
18:00  复盘：3 个目标闭环 → 每目标产出 1 张认知卡 → 提交 1 个 skill 候选
```

**产品的第一条验收标准**：上面这条动线，在 200 个 Agent 规模下能压缩到每天 45 分钟以内。

## 3. 产品形态与系统边界

### 3.1 形态

**本地部署的单机 Web 应用**，`docker compose up` 或一条命令启动，浏览器打开 `http://localhost:8700`。

不选 SaaS 的理由：① 你的密钥、账号、content 不能上第三方；② 500 个 Agent 的调度是 IO 密集不是算力密集，单机足够；③ 数据留在本地，调试成本低一个数量级。

### 3.2 三面结构

```
┌─────────────────────────────────────────────────────────┐
│  运营台（人看的）  Web 控制台 · 8 个页面 · 日报推送         │
├─────────────────────────────────────────────────────────┤
│  控制面（管事的）  目标 / 调度 / 预算 / 闸门 / 评估 / 账本   │
│                    ← 本产品的主体，全部自研 →              │
├─────────────────────────────────────────────────────────┤
│  执行面（干活的）  Worker 协议（4 个接口）                  │
│    WorkBuddy · Trae · Opencode · 云手机 · Mac mini        │
└─────────────────────────────────────────────────────────┘
         ↓ 统一出口
   能力网关（Provider 适配层）→ 上游 API / 设备 / 第三方服务
```

**核心边界**：控制面只认"能力 ID + 输入输出契约"，不认 Agent 是谁、用什么模型、跑在哪台机器上。这是"派给能力不派给 Agent"在软件上的落地方式。

### 3.3 Worker 协议（产品最重要的接口设计）

任何运行时接入只需要实现 4 个接口，这是生态能否成立的关键：

| 接口 | 作用 | 关键参数 |
|---|---|---|
| `POST /worker/claim` | 领活 | 我的能力标签、并发余量、机型 → 返回 task + lease |
| `POST /worker/heartbeat` | 续约 | task_id、进度百分比、当前步骤 |
| `POST /worker/complete` | 交货 | 产出、成本明细、步骤级 trace、耗时 |
| `POST /worker/fail` | 报错 | 错误类型（可重试/不可重试）、上下文 |

> 一个 Worker 最短 30 行代码就能接进来。这让"再开 100 个 Agent"从工程问题变成配置问题。

## 5. 核心对象模型

9 个对象，构成产品的"名词表"。所有页面都是它们的视图。

| 对象 | 是什么 | 关键字段 | 谁创建 |
|---|---|---|---|
| **Objective 目标** | 一次有预算、有期限、有止损的赚钱尝试 | 北极星指标、护栏、预算上限、TTL、止损阈值、状态 | 人 / 机会雷达 |
| **Capability 能力** | 可被调用的标准动作（如 `social.xhs.publish`） | 版本、输入输出契约、成本、成功率（含置信区间）、健康度 | 工程师 |
| **Provider** | 能力的某个具体实现方 | 上游名、单价、成功率、熔断状态、权重 | 工程师 |
| **Agent** | 一个可替换的工位 | 能力标签、状态、绩效、当前租约 | 注册（模板继承） |
| **Task 任务** | 最小执行单元 | 依赖、优先级、幂等键、租约、trace、成本 | 系统展开 DAG |
| **Effect 副作用** | 对外界的不可逆动作（发布/发消息/扣款） | 幂等键、内容哈希、状态 | 任务提交时 |
| **Approval 闸门** | 等人类点头的一次动作 | 风险等级、机器初审结论、决策、耗时 | 系统创建 |
| **Skill 技能** | 可复用的方法包 | 版本、eval 通过率、灰度比例、状态 | 训练流程 |
| **CognitionCard 认知卡** | 一条带触发条件与失效期的判断规则 | 触发条件、规则、置信度、反例、失效期、复用次数 | 复盘 |

> **一个刻意的设计**：Objective 与 Task 之间是"模板展开"关系，不是"人肉拆解"。目标卡里写 `拆解模板: 内容引流-v3`，系统自动生成 DAG。这是 500 规模的唯一可行方式。

## 6. 五条核心流程（产品的"动词"）

### 6.1 立项：从意图到可执行契约

```
双通道供给
├─ 下行：人写一句话 → 选模板 → 填预算/期限/止损 → 系统校验 → 目标卡
└─ 上行：机会雷达扫描 → 评分卡打分（≥70 进池 / 60-70 观察池 / <60 丢弃并记录原因）
                                                    ↓
                                        自动展开任务 DAG（模板）
                                                    ↓
                                    预算阀门登记（目标/小队/Agent 三级）
```

**产品化要点**：
- 立项表单里**必须**有"止损阈值"，且默认值由系统按同赛道历史 P25 自动填（不让用户拍脑袋）。
- 预算必须留 15–20% 预备金，护栏阈值默认设为目标 CPO 的 0.8 倍——**护栏要早于预算触发**。
- 评分卡权重可编辑，但页面要显示"该权重最近一次校准时间 + 敏感性提示"。

### 6.2 派活：能力匹配 + 租约

```
任务就绪（依赖满足 + 预算未超 + 未被闸门拦）
        ↓
按能力 ID 匹配可用 Agent（在线 && 空闲 && 能力标签命中 && 机型满足）
        ↓
派发 = 加租约（默认 90s）+ 心跳续约（30s）
        ↓
┌─ 正常完成 → 进入质检
├─ 心跳超时 → 回收 → attempts+1 → 重排队（≤3 次）
└─ attempts > 3 → 死信（人工处理，不静默丢弃）
```

**规格参数（可验收）**：

| 机制 | 参数 | 为什么是这个值 |
|---|---|---|
| 租约 | 90s，心跳 30s | 3 倍容错窗口；长任务用"分段租约"，避免长时间占用 |
| 回收上限 | 3 次 | 同一个活被 3 个 Agent 搞不定，说明是活的问题不是人的问题 |
| 幂等键 | `sha1(目标ID + 节点ID + 内容哈希)` | 覆盖发布类动作的重复投递 |
| 重试 | 指数退避，单任务上限 2 次 | 防止上游故障时烧穿预算 |
| 熔断 | 能力级 60s 窗口失败率 >30% → 开路 5min → 半开单探 | 与 Provider 健康度联动 |

### 6.3 交付：两层质检（这是 v0.1 最容易被砍、但最不能砍的部分）

**为什么要拆两层**：平台效果反馈延迟 24 小时到 2 周。快环只能查格式，查不了"有没有用"。混在一起会导致"通过率很高、业务在亏"。

| 层 | 时机 | 判什么 | 手段 | 覆盖 | 成本 |
|---|---|---|---|---|---|
| **L1 合规闸门** | 提交后秒级 | 违禁词、字数、链接、查重（近 30 天相似度 >70% 拦）、AI 标识、账号频次 | 规则引擎，100% | 全量 | 近零 |
| **L2 效果评估** | T+1 / T+7 / T+30 | 播放/互动/线索/转化是否达该 cohort 基准 | 分层对比 + holdout | 抽样 | 低 |

**产出三分类必须互斥且穷尽**：`通过 / 返工 / 废弃`（对应 75% / 15% / 10%）。当前方案写"75% + 15%"留下了 10% 未定义，会导致一次通过率虚高。

**CPO 的分母只算"T+7 仍达标"的产出**，不算提交量，也不算当天通过量。

### 6.4 闸门：抽样 + 阈值，不是全审

```
所有对外/不可逆动作 → 机器初审（规则 + 中等模型）→ 判风险等级
   ├─ 低（改写、抓取、内部分析）     5% 抽检
   ├─ 中（发布到自有账号、发邮件）   30% 抽检
   └─ 高（花钱 >¥500、品牌号发布、删数据、改配置） 100% 人审
```

**动态抽检**：以机器初审的漏判率为控制变量——漏判率 >5% 自动提档（5%→15%），连续 7 天为 0 则降档到 1%。这比固定比例更接近真实风控，也天然解决"人力不够"。

**容量约束（必须写进产品）**：`日动作数 × 加权抽检率 ≤ 人力日上限（约 60–80 条/人）`。系统要在闸门页顶部显示"今日预计审阅量 / 人力上限"，超了就自动降档并告警——而不是让人自己发现审不完。

### 6.5 复盘：认知卡 → skill（慢环，决定复利）

```
目标闭环 → 强制产出 ≥1 张认知卡（否则目标不算完成、不释放剩余预算）
        → 卡入卡库（触发条件硬过滤 + 语义召回）
        → 被引用 3 次以上 → 提名为 skill 候选
        → 案例采集（成功/失败各 20 例）→ 撰写 SKILL.md
        → 沙盒回放（40 例，成功率提升 ≥15% 才放行）
        → 灰度 10% / 3 天 → 全量 + 版本号
```

**产品化要点**：
- 卡库必须有**冲突消解**：新卡上线要声明"覆盖哪张旧卡"，同触发条件不允许两张"有效"卡并存。
- 每张卡带 **holdout 记录**（用了 vs 没用的对照），没有实验记录的卡只能标"假设"，不能进 skill。
- 卡过期自动转"待复核"，一年未复核归档——否则卡库半年就烂。

## 7. 指标定义（口径必须写死，否则数字会打架）

### 7.1 主指标：CPO（修正版）

```
CPO = (模型 + 工具 + 设备 + 返工 + 质检 + 人力摊销) ÷ T+7 达标产出数
```

六个分项各自独立上报，**不允许合并成一个"其他"**。理由：合并之后，CPO 一涨就没人知道该砍谁。

### 7.2 一屏 8 个指标（首页只显示这些）

| 指标 | 定义 | 健康区间 | 恶化时先看哪 |
|---|---|---|---|
| 今日达标产出 | T+7 口径回溯到今日的数量 | 环比持平或上升 | 任务流 |
| **CPO** | 见上 | 月环比 −8%~−12% | 成本页六分项 |
| 一次通过率 | 通过 ÷ (通过+返工+废弃) | ≥75% | Agent 绩效卡 |
| 返工率 | 返工 ÷ 总产出 | ≤15% | 能力健康度 |
| 预算偏差 | 实际 ÷ 预算 | ±8% 内 | 目标详情 |
| 队列等待 P95 | 从入队到领活的 95 分位 | <15 min | 能力/Provider |
| 人类介入次数 | 需人**决策**的次数（不含浏览） | ≤8 次/日 | 闸门页 |
| 在途任务 / 扇出 | 单 Lead 在途任务数；单任务跨 Agent 跳数 | <40 / <4 | 调度页 |

> 前 4 个是滞后指标，后 4 个是领先指标。**先看领先指标**——这是预警能提前一周的原因。

## 9. MVP 范围（这一节决定工期，请重点评审）

### 9.1 v0.1 必须做（4 周内可跑通）

| 模块 | 最小可用形态 | 验收标准 |
|---|---|---|
| 调度内核 | 队列 + 租约 + 心跳 + 回收 + 死信 | 杀掉一个 worker，任务 90s 内被重派，不重复执行 |
| 预算阀门 | 三级配额 + 90% 预警 | 超预算任务不再派发，页面可见 |
| 目标卡 | 创建/冻结/TTL/止损/模板展开 DAG | 建一个目标，10 秒内生成 ≥5 个任务的 DAG |
| L1 合规闸门 | 规则引擎（查重/违禁词/标识/频次） | 违规内容 100% 拦截，误杀率 <5% |
| 闸门与审批 | 风险分级 + 抽样 + 待审队列 | 高风险动作不经人审无法执行 |
| 成本账 | 六分项记账 + CPO 计算 | 任一产出可下钻到每一步成本 |
| Worker 协议 | 4 个接口 + 1 个示例 worker（模拟） | 一个新 worker 30 行接入并领到活 |
| 首页 | 8 指标 + 异常队列 | 打开 3 秒内看出"今天要不要管" |

### 9.2 v0.2 再做

任务流可视化、Agent 绩效卡与退役、能力/Provider 比价、认知卡库、日报推送、trace 抽屉。

### 9.3 明确不做（v1.0 之前）

- 多租户 / RBAC / SSO（单用户 + 一个共享口令）
- 可视化流程编辑器（用 YAML 模板，别做拖拽）
- 自动生成 skill（先人工，跑通 20 次再说）
- 移动端 App（日报走微信/邮件即可）
- 自研消息队列（Postgres 足够撑到 1 万任务/日）

> **砍掉的理由**：这些功能会让工期翻倍，但不会让"500 个管得住"这件事提前一天成立。

| 版本 | 周期 | 目标 | 毕业标准（达不到就不进下一版） |
|---|---|---|---|
| **v0.1 内核** | 4 周 | 一条业务线 30 个 Agent 跑通 | 连续 7 天无重复发布；CPO 可算；人日介入 ≤15 次 |

## 11. 成本模型（修正版，这一节替换原方案的第六节）

### 11.1 四情景对比（关键修正）

原方案用"全量大模型 ¥6/任务"做基线，得出 12.4 倍——这是稻草人：¥6 是**复杂任务**单价，复杂任务只占 5%。

| 方案 | 日成本 | 相对三层路由 |
|---|---|---|
| 全部中等模型，不升级 | ¥2,700 | 1.24x |
| 全部中等 + 复杂任务升级 | ¥3,915 | 1.79x |
| 三层精细路由 | ¥2,182 | 1.00x |
| ~~全量大模型（原基线）~~ | ~~¥27,000~~ | ~~12.37x~~ |

**结论要改**：分层路由相对"两档 + 升级"只多省 44%。而三层路由的成本里，62% 来自那 5% 的复杂任务——**真正的杠杆是把复杂任务拆小、降档，而不是把路由做细**。

### 11.2 六分项成本（新增）

| 分项 | 量级（月，150 Agent 基线） | 说明 |
|---|---|---|
| 模型 | ¥2.0 万 | 按 1,350 任务/日 × 混合单价 |
| 工具/订阅 | ¥0.6 万 | 固定订阅控制在总预算 20% 内 |
| 设备 | ¥1.2 万 | 安卓 10 台 + Mac mini 3 台（含闲置） |
| 返工 | +25~33% | 一次通过 75% → 25% 重做 |
| 质检 | +10~15% | Critic 模型 + 人工抽检工时 |
| **人力** | **¥9–12 万** | 3–4 FTE 全成本（**最大项**） |

**这张表最重要的含义**：人力是模型成本的 4–6 倍。所以"降本"的第一优先级不是换小模型，是**把人的时间从低价值环节挪走**（闸门自动化、eval 自动化、异常自动分类）。产品设计的很大一部分价值在这里。

### 11.3 CPO 目标

不设"总 CPO 月降 10%"这种笼统目标，改为分项：模型 −8% / 返工率 −3pct / 人力摊销 −5%。因为笼统目标会让人去压最容易压的那项（模型档位），而不是最难但最有价值的那项（返工率）。

## 12. 技术选型与"不自研"清单

| 组件 | 选择 | 理由 |
|---|---|---|
| 调度/工作流内核 | **第一版自研轻量版**（Postgres 队列 + 租约），超 5,000 任务/日再评估 Temporal | 自研 400 行就能到及格线，先省一次迁移 |
| 数据库 | **SQLite（单机）→ Postgres（并发 >50 worker）** | 迁移成本低，schema 一致 |
| 后端 | Python + FastAPI | 与 Agent 生态同语言，调试快 |
| 前端 | 原生 JS + 一页式控制台，无构建步骤 | 避免前端工程吃掉两周 |
| 观测 | OpenTelemetry trace（可选接 Langfuse） | 不自建 UI，先保证有数据 |
| 报表 | 系统内置 + 每日推送，不接 BI | Metabase 需要人维护，前 3 个月不值得 |

**不自研清单**：消息队列、可视化流程引擎、鉴权系统、BI、告警通道（用现成 webhook）。

## 13. 风险与红线

| 风险 | 概率 | 影响 | 产品侧的应对 |
|---|---|---|---|
| 平台限流/封号导致目标归零 | 高 | 极高 | 目标必须绑备用承接账号；账号健康分自动降频；查重 + 频次上限 |
| 提示注入（抓来的内容当指令执行） | 中 | 高 | 数据/指令分离：抓取内容只进结构化字段，永不进 system prompt |
| 500 个 Agent 成为 500 个外泄入口 | 中 | 高 | 密钥集中 + 15 分钟短期凭证 + 按"目标×能力×动作"授权 |
| AI 生成内容未标识（监管风险） | 中 | 高 | 《人工智能生成合成内容标识办法》2025-09-01 已施行，显式+隐式标识做成硬拦截 |
| 闸门退化成"点通过" | 高 | 中 | 显示"今日审阅量/人力上限"，超限自动降档并告警；记录审批耗时，过快自动抽检复核 |
| CPO 靠压质量假降 | 中 | 高 | CPO 必须与一次通过率、T+7 达标率同时看，三者背离即预警 |

**三条红线（写进产品，不可配置）**：
1. 高风险动作未经人审不得执行。
2. 不为规避 AI 标识做任何后处理。
3. 死信任务不得静默丢弃。

## 14. 待你拍板的 8 个决策

| # | 决策 | 选项 | 推荐 | 不决策的后果 |
|---|---|---|---|---|
| 1 | 部署形态 | 本地单机 / 云服务器 / 两者 | **本地优先**，云做只读镜像 | 影响密钥安全与访问方式 |
| 2 | 首个业务线 | 小红书引流 / 多平台并行 | **小红书单点** | 模板与规则库要做两套，工期 ×1.8 |
| 3 | Worker 协议 | 只接自家 / 开放 4 接口 | **开放** | 换运行时就要重写调度 |
| 4 | 调度内核 | 自研 / Temporal | **v0.1 自研**，5,000 任务/日再迁移 | 前期引入运维复杂度 |
| 5 | 用户体系 | 单用户 + 口令 / 多用户 RBAC | **单用户** | 至少多花 2 周 |
| 6 | 成本口径 | 只算 token / 含六项 | **含六项** | 看板数字不可信，决策失真 |
| 7 | 首个版本规模 | 30 / 100 / 150 | **30**（一条线跑通再加） | 直接上 150 会同时暴露 5 类问题 |
| 8 | 课程化 | 与 v0.1 并行 / v1.0 产出 | **v1.0 产出** | 前期为教学做抽象，拖慢主线 |

## 15. 评审通过后的第一步（不需要等你再确认）

若本稿通过，开发第一周只做三件事，且都可独立验证：

1. **任务生命周期状态机 + 租约回收**（可跑的压力测试：杀掉 worker 看是否重派且不重复）
