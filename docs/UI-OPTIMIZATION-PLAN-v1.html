2界面设计与交互优化的具体范围

三层范围：设计体系层 → 交互机制层 → 页面层。体系层先行，页面层消费，避免 10 个页面各改一套。

2.1 设计体系层（设计令牌 v1.1 + 组件库 v1.0）

范围项内容性质
暗色令牌组为现有 9 个语义令牌生成暗色对照组（prefers-color-scheme + 手动切换），组件零改动——这是语义化令牌的红利新增
复合组件数据表格（排序/空态/骨架行）、表单组（字段+校验+错误）、Toast/通知条、确认弹窗（含"不可逆操作"红色变体）、Drawer 详情、时间/金额/时长格式化器、状态色映射函数（复用 Tone）新增
信息密度规范控制台保持高密度（正文 13px 档）作为默认；只定义"关键数字"放大规则（今日页三数字），不全局放大字号规范
状态与反馈统一"加载/空/错误/重试"四态文案与视觉；告警一律 danger，不用 warn 冒充（沿用 globals.css 注释纪律）收口
动效预算只保留状态过渡（≤200ms），禁止装饰性动效；prefers-reduced-motion 全量降级规范

2.3 页面层（10 页 + 1 个候选页）

逐页优化清单见 §3 优先级表。共性要求：页首 3 秒内给出该页"问题句"的直接答案；空态给出下一步动作而非装饰插画；所有异步区走 AsyncBoundary 三态。

2.4 明确不做（防范围蔓延，与 W12 §9 纪律一致）

  • 不引入通用图表平台 / ECharts 全家桶（只做现有三视图的打磨，W12 已否决）
  • 不换组件库、不做主题引擎、不做用户自定义皮肤
  • 不做小程序三屏（T5 独立排期，依赖 ICP 备案）
  • 不改信息架构：10 页 + 分组（指挥/执行/资产/视图）不动；新增"缺席"导航项若发生，走 shared-registry 变更请求（nav.ts 是冻结文件）
  • 不做营销式落地页、不做动效包装

沿用仓库既有的窗口制与 Merge Marshal 机制，不新造流程。本计划在仓库语境下相当于一个跨页面优化波次，冻结文件纪律必须遵守。

角色职责关键交付物与节奏

后端（0.5 人）度量聚合接口（W12 #6 后半）、决策排班接口（W07-I07 若被 Marshal 采纳）、缺席/简报接口（W11 若排期）接口契约先行（OpenAPI 快照），前端按契约 mock 开发，不阻塞

5.1 协作规则

  • 契约先行：任何"前端等后端"的依赖，先冻结 OpenAPI 契约，前端用 openapi-typescript 生成类型 + mock 开发；后端到位后只联调不改设计。
  • 评审节点：每阶段末一次联合走查（设计+前端+产品本人），过出口标准才进下一阶段；G 系列目标逐项打勾。
  • 冻结文件：本计划默认不改 nav.ts / router.py；确需新增导航（缺席页）时，单独 PR 走 shared-registry 变更请求，不夹带在页面优化 PR 里。
  • 争议裁决：视觉品味争议由"是否减少你的认知负担"裁决；无法裁决时回到 v0.2 原文，原文没有的记录为新的待拍板项（§9）。

6前后端联调与测试验证

6.1 联调机制

OpenAPI 契约后端先出快照，gen:api 生成 schema.d.ts
→
前端 mock 开发react-query + apiFetch，三态走 AsyncBoundary
→
本地联调docker compose（db/redis/api/web）
→
staging 验证真实数据 + 度量埋点回传
→
生产灰度自用 3 天 + 指标对照
  • 错误语义统一走 apiFetch 的错误映射与重试策略，页面不自定义错误码处理；新增错误码须先登记 docs/ERROR-CODES.md。
  • 联调清单按依赖排序：度量聚合（阶段 0）→ 排班接口（阶段 1 尾，可降级为前端本地规则）→ KPI 填报（阶段 1，W12 #5 若采纳）→ 缺席/简报（阶段 3，W11 若排期）。每项有"未就绪降级方案"，无一阻塞主线。

层内容门禁
静态typecheck + build；新增 lint 规则：禁止页面层内联 hex、禁止自拼三态CI 必过
E2EPlaywright 由 4 spec 补齐至 10 页冒烟；关键交互（三问转目标、熔断出现、排班高亮、不可逆二次确认）用时间 mock 做分时段断言CI 必过（阶段 2 末起）
a11y现有 a11y spec 扩展至全站：对比度（暗色组必测）、键盘可达、focus 可见、reduced-motion 降级CI 必过（阶段 2 末起）
视觉回归对 10 页建立截图基线（Playwright 截图对比即可，不引入新平台）；令牌变更必须全量回归一次阶段 4 起入 CI
性能预算首屏 LCP ≤2.5s（staging 实测）；单页 JS 增量超预算（建议 ≤30KB gzip/页 Assumption）需在 PR 说明理由阶段 4 校验
人工验收每页"问题句 5 秒测试"；G1–G6 逐项签字每阶段末

7上线发布与后续迭代安排

环节安排
发布路径复用 W09 CI 门禁 + W12 #3 部署流水线（若该提案已落地；未落地则沿用现有 docker compose pull && up -d 手动路径并在风险表登记）。页面级改动独立 PR、独立可回滚（镜像 tag）。
灰度策略单人系统，灰度 = staging 自用 3 天：每日正常使用，度量埋点回传，与阶段 0 基线对照（停留时长、决策耗时、异常发现数）。无回归即推生产。
上线顺序度量埋点（阶段 0 末，最先）→ 令牌+暗色+组件库（阶段 1 中，纯体系可单独发）→ 指挥组三页 → 其余六页 → 视图与响应式 → 缺席页（接口就绪后）。每步独立发布，不做"大爆炸"合版。
效果回看发布后第 1、4 周各出一次对照周报（G1–G6 口径）；结果直接回答"这波优化值不值"，作为是否立项下一波 UI 工作的依据。
后续迭代① 缺席页真接口联调（随 W11 排期）；② 决策排班后端化（W07-I07，替换前端本地规则）；③ KPI 自动采集后的目标页增强（W12 #5 P2 部分）；④ 移动端"只看只批"体验深化（等 T5 小程序决策）。迭代需求一律进 backlog 由 Marshal 在 Wave 边界排期，不在本计划内追加。
