## 0. 先纠正三个前提（否则后面全要返工）

你提的四件事里有三个隐含假设需要先掰过来。这三条不改，方案做出来会卡住。

### 0.1 Vercel 不能承担主站，也不能被小程序调用

| 事实 | 后果 |
|---|---|
| 微信小程序的 request 合法域名必须 **HTTPS + 已 ICP 备案 + 加入白名单** | `*.vercel.app` 无法备案，小程序**不可能**直连 Vercel |
| 国内访问 Vercel 延迟高且有偶发不可达 | 主入口体验差，且你人在国内 |
| 备案绑定在**域名**上，不绑定在服务器上 | 域名备案后，可以随时换后端，不必锁死腾讯云 |

**结论**：**腾讯云是唯一的主站与 API**，域名为 `api.<你的域名>` 与 `app.<你的域名>`，都在腾讯云备案。
Vercel 保留但降级为两个用途：① **PR Preview**（每次改动自动出预览链接，这个非常值）；② 海外/备用访问。

> 如果你坚持 Vercel 做生产前端，那小程序必须走 `api.` 国内域名做代理，等于多一跳、多一处故障点，不划算。

### 0.2 "每小时上报"必须拆成三种频率

单一时钟 60 分钟上报，会带来一个致命问题：**你分不清"设备死了"和"设备在忙"**。最坏情况下 60 分钟才发现节点失联，而调度器在这 60 分钟里会持续往死节点派活。

| 通道 | 频率 | 内容 | 丢了会怎样 |
|---|---|---|---|
| **心跳** | 60 秒 | load、内存、磁盘、电量、活跃会话数、队列深度 | 3 次丢 → suspect；5 分钟丢 → offline，立即停止派活 |
| **增量** | 事件驱动，30 秒批量 | 任务事件、步骤 span、成本、错误 | 本地缓冲 + 游标续传，不丢 |
| **快照** | **60 分钟**（你说的"每小时"） | agent/orca/skill 版本、会话清单、能力变更、磁盘占用 | 缺一次不致命 |

**"每小时"是库存快照的节奏，不是心跳的节奏。** 这一条不拆，设备管理会一直"看起来正常但其实已经挂了"。

### 0.3 不要用 Grafana 做业务看板

Grafana（77.3k）强在**时序指标聚合**，弱在**对象状态机与拓扑**。你要看的是 `Issue → Worktree → Agent → PR` 的状态流转和"谁改重了文件"，不是 QPS 曲线。

用 Grafana 拼这类视图，实际做法是写一堆 SQL + 变量 + 嵌套面板，三个月后没人敢改。

**分工**：
- 业务视图（项目/Agent/设备状态）→ **自研**，用 React Flow（xyflow 38.7k）做底座
- 会话视图（Agent 说了什么、花了多少）→ **嵌 Langfuse**（36.0k），别自研
- 系统指标（CPU/队列/成本趋势）→ Grafana 可选，二期再说

## 1. 总体架构

单人维护的规模，**不要微服务**。一个后端 + 一个库 + 一个设备网关，全部跑在一台 4C8G 上，扩容前不需要动结构。

```
   浏览器 ────┐
              ├──► app.<域名>  (Next.js, Caddy 反代)  ──┐
   小程序 ────┘                                          │
                                                         ▼
   设备 Agent (Go) ──心跳/增量/快照──► api.<域名> ──► FastAPI ──┐
                                  (HMAC 签名)                  │
   Orca 主机 ──CLI + hooks────────► /ingest ───────────────────┤
                                                               ▼
                                                    Postgres（唯一真相源）
                                                    ├ tasks / leases / effects
                                                    ├ devices / heartbeats
                                                    ├ ledger / evals / skills
                                                    └ intakes / approvals
                                                               │
                              ┌────────────────┬───────────────┼──────────────┐
                              ▼                ▼               ▼              ▼
                        Langfuse(会话)     COS(产物/截图)   GitHub(Issue/PR)   Prometheus(可选)
```

**三条总线**：
1. **控制总线**：任务派发与租约（Postgres 队列，`FOR UPDATE SKIP LOCKED`）
2. **数据总线**：设备上报与事件（HTTP ingest，幂等序号）
3. **验收总线**：GitHub PR / CI 结果（外部 oracle，最可靠）

## 2. 技术选型（含 Star 数与取舍理由）

### 2.1 后端与数据

| 组件 | 选型 | Star | 为什么 | 不选什么 |
|---|---|---|---|---|
| API 框架 | **FastAPI** | **103.2k** | 异步、自动 OpenAPI（前端直接生成类型）、LLM 生态最顺 | NestJS（76.9k）也可，但双语言维护成本高 |
| ORM / 迁移 | **SQLAlchemy 2.0 + Alembic** | — | 成熟、可写原生 SQL（队列需要） | Prisma（不适合 Python） |
| 数据库 | **PostgreSQL**（腾讯云托管版） | — | `SKIP LOCKED` 直接当队列用；JSONB 存任务 payload；一个库解决 90% 需求 | 不要为了"架构感"上 Kafka/Cassandra |
| 队列 | **Postgres 自建**（约 400 行） | — | 你的量级（≤1 万任务/日）单表足够；少一个中间件就少一处故障 | Celery（29.0k，重、可观测差）；Airflow（47.2k）/Dagster（16.3k，是数据编排不是任务派发）；Temporal（23.8k，二期再评估） |
| 缓存/限流 | **Redis** | — | 只做限流、短期缓存、分布式锁 | 不要用 Redis 当队列（会和 PG 形成两套真相） |
| 模型网关 | **LiteLLM** | **61.5k** | 一个接口覆盖各家模型 + 成本核算 + 重试/降级，正好是你要的"中转 API" | 自己写多 Provider 适配（重复造轮子） |
| 反向代理 | **Caddy** | **78.1k** | 自动申请续期 HTTPS，配置 5 行 | Nginx（要自己配证书续期）；Traefik（配置更绕） |

**关于 Agent 编排框架**（LangGraph 43.4k / CrewAI 59.8k / AutoGen 61.5k / Dify 158.8k）：
**都不作为系统核心。** 理由：我们要的是"派活与验收"，不是"Agent 内部怎么想"。把这些框架当控制面用，会和我们自己的调度/预算/闸门重复，最后两套状态互相同步。它们只能作为**某个 Worker 的内部实现**（一个 Worker 用 LangGraph 写，对控制面来说仍然只是一个"领活-交货"的黑盒）。

### 2.2 设备端

| 组件 | 选型 | Star | 为什么 |
|---|---|---|---|
| Agent 语言 | **Go** | — | 单二进制、无运行时依赖、跨 Win/macOS/Linux、内存占用小。设备上装 Python 是最常见的失败原因 |
| 打包发布 | **GoReleaser** | **16.1k** | 一条命令出三平台安装包 + 校验和 |
| 常驻方式 | LaunchAgent（macOS）/ Windows Service / systemd | — | 开机自启、崩溃重启，不用用户管 |
| 协议 | HTTPS + HMAC 签名；指令下发用长轮询 | — | NAT 后的设备只能主动拉，WebSocket 在笔记本休眠场景不稳定，长轮询更耐操 |

> 不用 Python + PyInstaller：包体 50MB+、杀毒软件误报率高、Windows 上经常起不来。这是踩过坑的选择。

### 2.3 前端与可视化

| 组件 | 选型 | Star | 用途 |
|---|---|---|---|
| Web 框架 | **Next.js** | **143.1k** | 主控台 + PR Preview |
| 数据层 | **TanStack Query** | **50.5k** | 轮询/缓存/失效，省掉一半状态管理代码 |
| 拓扑图 | **React Flow (xyflow)** | **38.7k** | 项目视图、设备-任务关系图（自研底座） |
| 小程序 | **Taro**（37.7k）或 **uni-app**（41.6k） | — | 若想复用 React 组件选 Taro；若只做三屏，**微信原生最省事** |
| 图表 | 系统图表用 Grafana；业务图表用 Recharts/轻量方案 | — | 不要为几张图引入 ECharts 全家桶 |

### 2.4 可观测

| 组件 | 选型 | Star | 定位 |
|---|---|---|---|
| Agent 会话追踪 | **Langfuse**（自托管） | **36.0k** | 每次 Agent 调用的输入输出/成本/耗时，UI 现成，**直接嵌 iframe** |
| 指标 | OpenTelemetry Collector（7.7k）+ Prometheus（66.6k） | — | 设备与 API 的系统指标，二期 |
| 业务看板 | **自研**（React Flow） | — | 见第 6 节 |
| 备选一体化 | SigNoz | 32.4k | 想省事可替代 Grafana+Jaeger，但资源占用高 |

**明确不用**：Uptime Kuma（92.6k，我们的心跳已覆盖，多一套系统多一处误报）、Netdata（81.0k，太重）、 Beszel（26.3k，可选做主机资源补充）。

## 3. 部署拓扑与规格

### 3.1 腾讯云侧

| 组件 | 规格（一期） | 说明 |
|---|---|---|
| 云服务器 / 轻量 | **4C8G，100GB SSD** | API + PG + Caddy + 前端全在一台，够跑到 150 个 Agent |
| 域名 | `app.` / `api.` 两个子域 | **必须 ICP 备案**（小程序硬要求） |
| 对象存储 COS | 标准存储 50GB | 截图、产物、trace 归档、数据库备份 |
| 镜像仓库 TCR | 免费额度 | 存放后端与前端镜像 |
| 备份 | 每日 `pg_dump` → COS，保留 30 天 | 单机最大的风险是"库没了" |

**成本估算（一期）**：服务器 ¥200–260/月 + COS ¥10 + 域名 ¥60/年 + 备案 ¥0 ≈ **¥300/月**。

### 3.2 关键路径：备案

**ICP 备案需要 2–3 周，且是纯等待。** 如果小程序是目标之一，**今天就要启动备案**，否则 P3 会被卡死。这是整个项目唯一无法用人力压缩的环节。

### 3.3 Vercel 的角色

| 用途 | 配置 | 说明 |
|---|---|---|
| PR Preview | 连接 GitHub，每个 PR 出 `pr-123.vercel.app` | 开发期最实用的功能 |
| 备用前端 | `preview.<域名>` CNAME 到 Vercel | 只读，指向 `api.<域名>` |
| 生产 | **不承担** | 国内访问不稳 + 小程序不可用 |

### 3.4 部署流程

```
git push → GitHub Actions
   ├─ lint + test
   ├─ build 镜像 → 推 TCR
   └─ ssh 到服务器 → docker compose pull && up -d
```

用 Docker Compose 而不是 K8s：单人维护，K8s 的运维成本远超收益。等真的需要多机再考虑。

## 4. 设备接入层（本轮重点）

### 4.1 设备身份与能力标签

| 字段 | 说明 |
|---|---|
| `node_id` | UUID，首次注册生成，与机器指纹绑定（防重复注册） |
| `token` | 注册时一次性下发，仅存哈希；设备端加密保存 |
| `os / arch / cpu / mem` | 自动上报 |
| **能力标签** | `has_gui`、`has_browser`、`orca`、`android`、`docker`、`gpu` |
| `tolerance` | `can_sleep` / `always_on` —— **决定派什么活给它** |
| `squad / purpose` | 归属与用途 |
| `trust` | `own` / `third_party`（第三方平台不接收指令下发） |

### 4.2 三种上报（对应 0.2 节）

**心跳（60s，<1KB）**
```json
{"node":"n-7f3a","ts":1759412345,"seq":88213,
 "load":0.62,"mem":0.71,"disk":0.44,"battery":0.82,
 "sessions":3,"queue":0,"agent_ver":"0.4.2"}
```

**增量（30s 批量，游标续传）**
```json
{"node":"n-7f3a","from_seq":88200,"to_seq":88213,
 "events":[{"kind":"task.done","task":"T-0412","cost":0.18,"ms":42000},
           {"kind":"span","task":"T-0412","node":"write","model":"claude","cost":0.09}]}
```

**快照（60min，你说的"每小时"）**
```json
{"node":"n-7f3a","ts":1759412345,
 "versions":{"agent":"0.4.2","orca":"1.9.3","skills":{"web-scaffold":"1.4.2"}},
 "sessions":[{"id":"s-31","task":"T-0412","state":"running","worktree":"/w/123"}],
 "caps":["has_gui","orca"],"disk_used_gb":48.2}
```

### 4.3 离线、休眠与时钟（这是设备层最容易翻车的地方）

| 问题 | 解法 |
|---|---|
| 笔记本休眠 → 积压大量事件 | 本地 SQLite 缓冲，唤醒后**先发快照再发增量**，避免服务端按顺序误判 |
| 网络切换（Wi-Fi→热点） | 身份不变，只重连；重连后带 `last_seq` 补齐 |
| 缓冲区爆掉 | 上限 100MB / 7 天，超限丢最旧并记 `dropped_count`（**必须上报，不能静默丢**） |
| 设备时钟不准 | 服务端记 `received_at` 为准，设备 `occurred_at` 只用于排序；偏差 >5min 打标并告警 |
| 重复投递 | 每条带 `(node_id, seq)` 单调序号，服务端唯一索引去重（**幂等的基础**） |
| 节点"假在线" | 心跳 3 次丢 → `suspect`（停止派新活）；5 分钟丢 → `offline`（回收租约） |

### 4.4 能力矩阵：什么设备干什么活

| 设备 | GUI | Orca | 浏览器自动化 | 容器 | 可休眠 | 适合派什么 |
|---|---|---|---|---|---|---|
| 常用 Mac 主机 | ✅ | ✅ | ✅ | ✅ | 否 | 开发、桌面自动化、Orca 宿主 |
| 远程 Mac mini | ✅ | ✅ | ✅ | ✅ | 否 | 常驻 Agent、iOS 生态、夜间批处理 |
| Win/Mac 笔记本 | ✅ | ✅ | ✅ | ⚠️ | **是** | 轻任务、需人工在旁边的任务 |
| 云服务器 VPS | ❌ | ⚠️ | 无头浏览器 | ✅ | 否 | 抓取、计算、常驻、重活 |
| 第三方平台 | ❌ | ❌ | 平台内 | ❌ | — | 纯 API 能力（不接指令） |

**调度含义**：任务必须声明 `requires`（`gui` / `orca` / `browser` / `always_on`）。**不匹配就不派**。
特别地：`requires.always_on = true` 的任务**绝不派给笔记本**——这是"任务莫名卡住"的头号原因。

### 4.5 指令下发（P3 再做）

设备在 NAT 后面，只能**设备主动拉**：

| 指令 | 说明 | 风险级别 |
|---|---|---|
| `collect_snapshot` | 立即上报一次快照 | 低 |
| `drain` | 不再领新活，做完在途的 | 低 |
| `restart_agent` | 重启 agent 进程 | 中 |
| `run_task` | 立刻执行指定任务 | 中 |
| `collect_logs` | 打包上传日志 | 低 |

**白名单制，永不支持任意 shell。** 中风险指令需控制面二次确认。第三方平台设备一律不接收指令。

## 5. Orca + GitHub Issue 的开发流

### 5.1 三方分工（不要互相抢职责）

| 角色 | 负责 | 不负责 |
|---|---|---|
| **我们的控制面** | 任务、预算、验收、账本 | 代码怎么改 |
| **GitHub** | Issue（任务的外部镜像）、PR、CI | 调度 |
| **Orca** | 隔离 worktree、跑编码 Agent、会话与 steer | Issue 状态管理 |

**关键**：真相源只有一处——**任务与预算在 Postgres，验收信号在 GitHub（PR merged / checks passed）**。不要双向同步 Issue 状态，会打成一团。

### 5.2 一个 Issue = 一个 Worktree = 一个分支

```
分支：issue/123-fix-upload-timeout
目录：.worktrees/123-fix-upload-timeout
声明：<worktree>/.fleet-task.json   ← 上一轮已定义，任务自解释
```

### 5.3 "一个窗口认领多个 Issue"的正确做法

你要的是"一个对话里能认领多个 Issue、每个完成就提交"。这里有个真实冲突必须先讲清：

> **认领多个 ≠ 并行改多个。** 在同一个上下文里同时改 3 个 Issue，会导致 ① 工作区互相污染 ② Agent 忘记当前约束 ③ 出错后无法定位是哪个 Issue 引入的。

正确做法是**「认领多个，执行一个，状态外置」**，三段式：

**第 1 段 · 认领（一次做完）**
```
列出本次认领的 3 个 Issue，按"依赖 → 风险 → 价值"排序
写进 .orca/plan.md：123 → 124 → 125（含依赖说明）
只认领，不开工
```

**第 2 段 · 分段执行（严格串行）**
```
一次只做 1 个 Issue：
  改代码 → 跑测试 → commit → push → 更新 .orca/handoff.md → 关掉该 Issue 的上下文
```

**第 3 段 · 交接（抗打断的核心）**
```
下一个 Issue 从 handoff.md 开始，而不是从完整对话历史开始
handoff.md ≤ 10 行：改了什么 / 没改什么 / 下一步 / 坑在哪
```

**原理**：上下文是易失的，文件是持久的。**把状态外置到 handoff.md，才可能"随便什么时候被打断都不丢"。**

### 5.4 抗打断的四条硬约定

| 约定 | 具体做法 | 解决什么 |
|---|---|---|
| **小步提交** | 每完成一个可运行增量就 commit（允许 WIP），立即 push | 断电/崩溃最多丢 30 分钟 |
| **早开 Draft PR** | 第一个 commit 就开 Draft PR，持续更新 | 进度对你自己可见，且 CI 每次都跑 |
| **提交带 Issue 号** | `feat(#123): 修正上传超时` | 事后可追溯，自动关联 |
| **handoff 随提交更新** | 每次 commit 前刷新 `handoff.md` | 接手成本 ≤5 分钟，人和 Agent 都适用 |

再加一条：**每 30 分钟自动 checkpoint commit**（用 Orca hook 或 git alias），哪怕没写完也提交到分支。分支本来就是草稿区，脏一点没关系。

### 5.5 验收信号怎么来（这是最省事的一环）

```
PR checks 通过 + PR merged  →  任务 verdict = ok  →  计入 CPO
PR closed 未合并            →  verdict = rework
CI 失败 3 次                →  熔断，转人工
```

GitHub 是天然的 oracle，**比让模型自评可靠一个数量级**。这也是为什么 coding 类任务适合这套系统——它有客观的对错。

## 6. 可视化：开源项目调研与推荐组合

### 6.1 你要的三个视图，本质是三种数据形状

| 视图 | 数据形状 | 谁来做 | 为什么 |
|---|---|---|---|
| **总视图**（所有项目） | 卡片墙 + 状态灯 | 自研 | 没有现成产品匹配"多项目 + 多设备 + 预算" |
| **项目视图**（同项目多 Agent） | 拓扑 / 甘特 | 自研（React Flow） | 核心是"发现冲突"，不是"看着爽" |
| **会话视图**（单个 Agent） | 时间线 + 树 | **嵌 Langfuse** | 自研要 2 个月，且做不到它那么细 |

### 6.2 候选对比（Star 数为实测）

| 项目 | Star | 强项 | 判断 |
|---|---|---|---|
| Grafana | **77.3k** | 时序、告警、生态 | ⚠️ 只做系统指标，**不做业务视图** |
| Langfuse | **36.0k** | LLM trace、成本、会话回放 | ✅ **直接嵌**，省两个月 |
| Temporal UI | 23.8k（Temporal） | 工作流执行树 | 二期若用 Temporal 则白送 |
| React Flow (xyflow) | **38.7k** | 节点图、拖拽、自定义 | ✅ **自研底座** |

### 6.3 推荐组合

```
总视图      → 自研：项目卡片墙 + 设备热力 + 待决策队列（Next.js + TanStack Query）
项目视图    → 自研：React Flow 拓扑 + 甘特（谁在哪个 Issue、有没有撞车）
会话视图    → iframe 嵌 Langfuse（按 task_id 跳转）
系统指标    → Grafana（可选，二期）
```

### 6.4 项目视图的设计要点（这条最值钱）

多数"Agent 看板"做成了一堆跳动的小方块，看着热闹但没用。**可视化的目的不是"看见它在跑"，是"发现三件事"**：

1. **撞车**：两个 Agent 改了同一批文件 → 高亮冲突文件
2. **阻塞**：某任务卡在等依赖/等审批 → 在图上标红并显示等了多久
3. **偏离**：某个 Agent 的产出与 Issue 目标不符（改了无关文件）→ 标黄

**"同项目多 Agent"的正确画法**：横轴时间、纵轴 Agent 的**甘特图**，每个条是一个 Issue 的占用区间。一眼能看出：有没有两个 Agent 在同一时间改同一块、有没有长时间空白（闲置）、有没有超时。

设备视图则用**热力格**：每台设备一格，颜色 = 状态（空闲/忙碌/可疑/离线），点击展开其承载的会话。

## 7. 小程序定位（只做三件事）

| 做 | 不做 |
|---|---|
| **看**：今日 ≤8 条决策 + 3 个数字 | 不做图表、不做全量列表 |
| **记**：一句话/语音进 Inbox | 不做编辑、不做富文本 |
| **批**：闸门 1–2 条高风险 | 不做任务创建、不做复杂配置 |

**技术要点**：
- `request` 合法域名填 `api.<域名>`（已备案）
- 登录用微信 `code2session` → openid 白名单（**单用户系统，不做注册**）
- 提醒用**订阅消息**，每天最多 3 条、21:00 汇总推送。**不要即时推送**——那会直接违背"带宽优先"的整个设计

## 8. 分阶段落地（与 v0.2 的 P0–P3 对齐）

| 阶段 | 周期 | 技术范围 | 验收 |
|---|---|---|---|
| **T0 地基** | 1 周 | 腾讯云 1 台 + Docker Compose + Caddy + PG + FastAPI 骨架 + Next.js 首页 | 外网可访问，HTTPS 正常 |
| **T1 单设备** | 1 周 | Go agent（macOS 优先）+ 三种上报 + 设备列表页 | 关机 5 分钟内显示 offline，唤醒后补齐事件 |
| **T2 多设备** | 1.5 周 | Windows/Linux 打包 + 能力标签 + 调度约束 | 笔记本休眠不卡任务；VPS 无 GUI 任务拒绝派发 |
| **T3 开发流** | 1.5 周 | GitHub App/Actions + Issue 同步 + Orca 接入 + handoff 约定 | 一个 Issue 从认领到 PR merged 全链路可追溯 |
| **T4 可视化** | 2 周 | React Flow 项目视图 + 总视图 + Langfuse 嵌入 | 能一眼看出撞车/阻塞/偏离 |
| **T5 小程序** | 1 周 | 看/记/批 三屏 + 订阅消息 | **依赖备案完成** |

**并行启动**：T0 的第一天就去提交 ICP 备案。备案与开发互不阻塞，但它决定 T5 能不能按期。

## 9. 成本（一期 / 二期）

| 项 | 一期（≤20 设备，≤50 Agent） | 二期（≤100 设备，≤150 Agent） |
|---|---|---|
| 云服务器 | ¥240/月 | ¥600/月（4C8G → 8C16G 或加一台） |
| 对象存储 + 流量 | ¥15/月 | ¥80/月 |
| 域名 | ¥60/年 | 同 |
| Vercel | ¥0（Hobby 够用） | ¥0–140/月 |
| 模型 API | 按量，¥500–2,000/月 | ¥5,000–20,000/月 |
| 设备（自有） | ¥0 | 按需 |
| **合计（不含模型）** | **≈¥260/月** | **≈¥700–800/月** |

> 结论：基础设施成本可以忽略，**真正的成本是模型调用和你自己的时间**。所以架构上不必为省服务器钱做复杂设计，要为"少踩坑"做简单设计。

## 10. 风险

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| **ICP 备案拖延** | 高 | 高（卡死小程序） | 今天就提交；小程序不阻塞主线 |
| 国内访问 Vercel 不稳 | 高 | 中 | 主站不上 Vercel，只做 preview |
| 设备 token 泄露 | 中 | **极高** | token 只存哈希、可单独吊销、指令白名单、第三方设备不收指令 |
| 笔记本休眠导致任务卡死 | 高 | 中 | 能力标签 + `always_on` 约束 + 心跳 suspect 即停派 |
| 单机 PG 故障 | 低 | **极高** | 每日 dump 到 COS + 每周做一次**恢复演练**（不做演练的备份等于没有） |
| 事件积压撑爆磁盘 | 中 | 中 | 缓冲上限 + 丢弃计数上报 + 磁盘水位熔断 |
| Orca CLI 变动 | 高 | 中 | `probe()` 自检 + 契约测试；失败即拒绝派活，不猜 |
| 一个窗口多 Issue 上下文污染 | 中 | 中 | 严格串行 + handoff.md 外置状态 |
| 自研可视化拖成无底洞 | 中 | 中 | 只做三个视图，不做通用图表平台；会话视图直接嵌 Langfuse |

## 11. 待你拍板

| # | 决策 | 选项 | 推荐 | 后果 |
|---|---|---|---|---|
| 1 | 主站是否放腾讯云 | 是 / Vercel 为主 | **腾讯云** | Vercel 为主则小程序做不了 |

> **一句话**：架构上只做一个后端、一个库、一个设备二进制；复杂度全部留给"设备状态的真实性"和"任务的可追溯"，而不是服务拆分。**能用一台机器解决的，不要用两台；能用 Postgres 解决的，不要加中间件。**
