## 0. 本次修订的三个根本变化

你这次补充的信息里，有三条足以推翻 v0.1 的骨架。我先摆出来，因为它们决定后面所有设计。

| # | v0.1 的假设 | 你这次说的 | 后果 |
|---|---|---|---|
| 1 | 目标来自"机会雷达扫描 + 评分卡打分" | **目标主要来自你的体感**，AI 捕捉只是补充 | 评分卡降级为"辅助"，产品核心变成**把体感变成契约**；否则系统会产出一堆"数据上该做、你不想做"的目标，最后没人执行 |
| 2 | 第一约束是预算（token 钱） | **脑基的认知带宽与体力带宽有上限** | 第一约束从"钱"换成"**你的注意力**"。所有界面、所有机制都要围绕"省你的脑子"重做 |
| 3 | 产品是"运营后台"（8 个页面的管理台） | 使用者是**一个人**，还要兼顾赚钱、读书、数学、熵减 | 形态从"后台"变成"**个人指挥台**"：不是展示信息，是压缩信息 |

**一句新定位**：

> 这不是"管理 500 个 Agent 的系统"，是**用 500 个 Agent 放大一个人的带宽**的系统。
> 500 个 Agent 每天会产生几千个动作，而你的决策上限大概是每天 40 个。**产品的全部技术难度，在于那 200:1 的压缩比。**

这个定位一变，很多东西跟着变：500 不再是目标，是**上限**；"管得住"的定义不再是"不重复派活"，而是"**你不被它拖垮**"。

## 1. 三个必须先算清的数字

在讨论功能之前，先把带宽这笔账算清。以下数字是估算（需你用一周真实记录校准），但量级决定了设计方向。

| 数字 | 估算 | 依据 | 含义 |
|---|---|---|---|
| **每日可用深度决策时间** | 120–180 min | 扣掉工作、通勤、生活后剩下的"能想事"的时间 | 这是硬上限，不可扩 |
| **单个决策的真实成本** | 3–5 min | 含读上下文 + 判断 + 记录，不含切换损耗 | 一天理论上限 30–40 个决策 |
| **可承受的日决策数** | **8–15 个** | 留出 50% 余量给突发与情绪波动 | 超过这个数，决策质量会断崖式下降 |

于是核心矛盾浮出来：

```
500 个 Agent × 每天 6 个动作 = 3,000 个待判断事件
你的带宽                     = 8–15 个决策
需要的压缩比                 = 200 : 1
```

**200:1 不可能靠"更好的看板"实现**，只能靠三件事：机器承担绝大部分判断、人只看例外、以及**主动减少派活量**。

所以本方案有一个和常规"效率工具"相反的原则：

> **产品要敢于对你说"今天别做了"。** 一个只会增加信息的系统，在这个场景下是负资产。

## 2. 目标体系（本次重写的核心）

### 2.1 入口：体感必须先被接住，才可能变成目标

你的原话是"目标主要来自于我的体感"。这句话的产品含义是：**在体感出现的那 30 秒内，如果没有入口接住它，它就消失了。**

所以第一个模块不是目标管理，是**收件箱（Inbox）**：

| 设计要点 | 具体做法 | 为什么 |
|---|---|---|
| 记录成本 ≤ 30 秒 | 手机快捷指令 / 桌面悬浮窗 / 微信给自己发消息（三选一，甚至语音） | 体感是易失的；要求"填表单"就等于杀死它 |
| 不要求完整 | 只存一句话 + 时间 + 当时场景 | 完整性由 AI 事后补，不占用你的带宽 |
| AI 三问结构化 | 24 小时内，AI 用三个问题把它变成契约 | 把"想法"变成"可验收的事"，这是系统存在的理由 |
| 允许烂在收件箱 | 超过 14 天没被结构化 → 自动归档为"兴趣"，不打扰 | 大部分体感本来就该被丢弃，逼你处理是反人性的 |

**AI 的三问（固定，不可增删）**：

1. **做完之后，什么变了？**（验收标准——没有这一条就不是目标，是愿望）
2. **多久内想看到结果？**（TTL——不给期限的目标会变成永久负担）
3. **愿意为它花多少？**（预算——赚钱目标填钱，进化目标填"每周几小时"）

三问答完，直接生成目标卡。**如果第一问答不出来，AI 应该建议"先放进兴趣池"，而不是硬造一个目标。**

### 2.2 双轨目标：赚钱与进化，是两种不同的东西

这是本稿最重要的结构性设计。你把目标分成"赚钱"和"认知进化"，但它们的**验收方式、预算货币、失败代价完全不同**。如果混在一套模板里，进化目标会被赚钱目标的 KPI 逻辑压死（"读这本书的 ROI 是多少？"——这个问题本身就是错的）。

| 维度 | **赚钱目标** | **进化目标** |
|---|---|---|
| 来源 | 体感 / 客户需求 / 机会雷达 | 体感 / 兴趣触发 / 随机遇到 |
| 成功定义 | 北极星指标 + 护栏 | **产出了可复用的认知资产** + 一次能力验证 |
| 预算货币 | 钱（¥）为主，注意力为辅 | **注意力（小时）为主**，钱几乎为 0 |
| 验收时点 | T+7 / T+14 / T+30 | T+7 交付物 / T+30 复用一次 |
| 止损逻辑 | 产出 < 历史 P25 → 冻结 | T+7 无任何产出物 → 降级为"兴趣"，不算失败 |
| 失败代价 | 亏钱（可再赚） | **浪费时间（不可再生，更贵）** |
| 典型指标 | CPO、线索成本、毛利率 | 卡片产出数、复用次数、能力雷达变化 |
| 系统该做什么 | 加速、降本、放大 | **限制投入**、防沉迷、保证产出物落地 |

**注意最后一行**：对赚钱目标，系统要"帮你多做"；对进化目标，系统要"帮你少做但做完"。这两个方向相反，必须用两套逻辑。这是很多"个人知识管理"工具失败的原因——它们对所有事都用同一套"鼓励你输入"的逻辑。

### 2.3 模板库（按你给的清单逐一落地）

你的清单可以直接映射成 8 个模板。模板的作用不是限制，是**让"三问"有默认答案**，把 3 分钟压缩到 40 秒。

**赚钱轨（3 个）**

| 模板 | 适用 | 北极星 | 护栏 | 拆解方式 |
|---|---|---|---|---|
| **A. 内容引流** | 小红书等平台获客 | 有效线索数 | 违规 0 次、单线索成本上限 | 选题 → 生产 → 发布 → 承接（4 节点） |
| **B. 企业服务** | 给企业主交付（代运营/Agent 落地） | 验收通过的交付物数 / 回款额 | 交付延期 ≤0、客户投诉 0 | 需求确认 → 方案 → 交付 → 验收（含人工节点） |
| **C. 知识产品** | 课程、模板包、咨询 | 付费人数 / 完课率 | 退款率 ≤5%、承诺不夸大 | 大纲 → 单节生产 → 试讲 → 上架（见第 7 节） |

**进化轨（5 个）**

| 模板 | 适用 | "产出物"是什么（验收物） | 防沉迷机制 |
|---|---|---|---|
| **D. 阅读与观影** | 书籍、影视、访谈 | **一张认知卡**（不是读书笔记）：触发条件 + 判断规则 + 反例 + 置信度 | 每周 ≤2 本；无卡不算完成 |
| **E. 数学** | 数学学习与训练 | 一道独立解出的题 + 解题路径卡（错在哪、为什么） | 单次 ≤45 min，超时强制停 |
| **F. 想象力开拓** | 跨领域输入、访谈、冷门题材 | 一个"可迁移的类比"（把 A 领域的机制映射到 B） | 每月 ≤4 次深挖，其余只收藏 |
| **G. 熵减** | 设备 / 数据 / 物品 / 订阅 | **可计量的减少量**（省下的钱、释放的 GB、减少的维护次数） | 天然有终点，做完即关 |
| **H. 生活黑客** | 流程优化、省钱攻略 | 一个可复用的 checklist 或自动化脚本 | 只保留"能跑起来"的，不做研究型收藏 |

> **D 类模板的关键设计**：读书目标不以"读完"为验收，以"产出一张卡"为验收。因为读完是消费，卡片是生产。这一条会把你的阅读行为从"输入焦虑"改成"输出驱动"。

### 2.4 G 类（熵减）应该成为第一个真实目标

这是一个明确建议：**MVP 的第一个目标不要选"小红书引流 500 线索"，选"订阅审计 + 设备清理"。**

理由有五条，每条都指向"降低第一次失败的概率"：

1. **30 天内可验证**——省下的钱当月就能看到，不需要等平台反馈。
2. **不依赖外部平台**——不用账号、不用设备、不怕限流封号。
3. **失败代价低**——最坏情况是白花几小时，不会亏钱。
4. **直接产生现金**——订阅审计（找出重复/未用/可降级的订阅）通常能省 5–15% 的固定支出。
5. **顺带验证 Agent 的核心能力**——读取账单、交叉比对、生成清单、执行取消，这是完整的"感知-判断-动作"链路。

而且它天然符合"体感驱动"：你自己就有"东西太多、乱、花了冤枉钱"的体感。

## 3. 第一约束：带宽（新增，且是全篇最重要的一节）

### 3.1 决策四层分级

这是把"认知带宽上限"翻译成产品机制的唯一办法：**先决定哪些决策绝对不给你，再谈界面。**

| 层 | 决策类型 | 谁做 | 日上限 | 例子 | 产品的责任 |
|---|---|---|---|---|---|
| **L0 战略** | 立项、砍目标、预算分配、方向调整 | **你，必须** | **≤2 个** | 这个月做不做内容引流 | 把决策成本压到 5 分钟内：给 2 个选项 + 推荐 + 不做的后果 |
| **L1 例外** | 高风险动作、异常、冲突、超预算 | **你，抽样** | **≤8 个** | 这条内容要不要发品牌号 | 机器先初审，只把"机器不确定"的递上来 |
| **L2 常规** | 派活、重试、路由、降级、配额内采购 | 机器 | 不限 | 这个任务派给小模型 | 你只需事后看抽检结果 |
| **L3 机械** | 心跳、清理、备份、归档、去重 | 机器 | 不限 |  nightly 快照 | 完全不可见，只在失败时告警 |

**关键**：L2/L3 不是"自动化"这么简单，而是**你必须放弃对这些事的控制权**。如果你每天还在看"任务派给了谁"，那这套系统就没成立。

### 3.2 三个带宽指标（和 CPO 并列）

| 指标 | 定义 | 目标 | 恶化时怎么办 |
|---|---|---|---|
| **决策负载** | 你当天实际做的 L0+L1 决策数 | 8–15 | >15 自动降级：非紧急任务转明日队列 |
| **信息压缩比** | Agent 动作数 ÷ 你的决策数 | ≥30:1（v1.0 ≥100:1） | 说明机器初审太弱，或你在看不该看的东西 |
| **注意力成本** | 每个达标产出消耗的你的分钟数（min/outcome） | 逐月下降 | 说明返工或异常太多 |

> `min/outcome` 是这个场景下最诚实的指标。它比 CPO 更贴近你的真实痛感：钱可以再赚，你的下午不能。

### 3.3 带宽熔断（保护你，而不是保护系统）

这是本稿独有的一个机制，常规管理工具不会有：

| 触发 | 系统动作 |
|---|---|
| 单日决策数 > 20 | 除"高风险"外全部转明日；页面顶部只显示一句"今天到此为止" |
| 连续 3 天决策耗时上升 50% | 自动降低派活量 30%，并提示"可能是疲劳导致的判断漂移" |
| 否决率突然从 10% 升到 40% | 提示"你在批量拒绝，可能是疲劳"，并抽 3 条要求复核 |
| 深夜（23:00–07:00）的 L0 决策 | 一律不给结论，只记录为"待明日确认" |

**为什么要做"否决率异常"检测**：人在疲劳时会进入"一律拒绝"或"一律通过"两种模式，两者都会造成损失。系统能看见模式，你看不见自己。

### 3.4 决策排班

不是所有决策都该随时做。系统应按"决策质量随时间衰减"来排：

| 时段 | 适合 | 不适合 |
|---|---|---|
| 上午 9–11 点（清醒） | L0 战略：立项、砍目标、定价 | 琐事 |
| 下午（易疲劳） | L1 例外：审批、异常处理 | 新目标决策 |
| 晚上（放松） | 体感捕捉（Inbox）、阅读 | 任何不可逆决策 |

产品上体现为：**Inbox 永远可用，立项按钮只在上午高亮，不可逆操作下午需要二次确认。**

## 4. 系统结构：五面（替代 v0.1 的七层）

v0.1 的七层是为"组织"设计的，单人使用时过重。压成五个平面，每个平面对应一个你能感知的东西：

```
┌──────────────────────────────────────────────────────┐
│  ① 目标面    你想干什么        Inbox · 双轨卡 · 模板库   │
├──────────────────────────────────────────────────────┤
│  ② 调度面    谁在什么时候干    队列 · 租约 · 预算 · 派活  │
├──────────────────────────────────────────────────────┤
│  ③ 执行面    用什么手干        Worker 协议 · Orca · 设备 │
│              能力从哪买        中转 API · Composio · Perflo│
├──────────────────────────────────────────────────────┤
│  ④ 资产面    怎么越干越强      能力档案 · 模型雷达 · skill│
│                              harness 模板 · 认知卡 · 课程│
├──────────────────────────────────────────────────────┤
│  ⑤ 治理面    值不值、要不要停  双币种账本 · 闸门 · 熔断  │
│                              **带宽预算**（横切）        │
└──────────────────────────────────────────────────────┘
```

**与 v0.1 七层的映射**（避免读者断层）：

| v0.1 | v0.2 | 变化 |
|---|---|---|
| L0 目标 | ① 目标面 | 评分卡降级，Inbox 升为主入口，双轨拆分 |
| L1 调度 | ② 调度面 | 增加"带宽阀门"（不只预算阀门） |
| L2 智力 | ④ 资产面的"模型雷达" | 从"层"变成"测评+路由表"这一具体机制 |
| L3 工具 + L4 资源 | ③ 执行面（合并） | 工具与采购合并，因为决策主体相同 |
| L5 能力 | ④ 资产面 | 增加 harness 模板化与课程产出 |
| L6 容量 | ② 调度面的子模块 | 降级（单人场景不需要独立层） |
| L7 治理 | ⑤ 治理面 | 增加带宽预算这一横切约束 |

## 5. 新模块详解（你这次新增的四件事）

### 5.1 模型能力雷达（你说的"AI 大模型测评感知能力上限"）

**要解决的真问题**：不是"哪个模型最强"，而是"**哪类任务现在根本做不到，所以别立项**"。这决定了你能不能拒绝一个听起来很好的目标。

| 设计项 | 做法 |
|---|---|
| 题面 | **用你自己的 20 个真实任务**，不用公开榜单。榜单和你的任务分布相关性低，哪怕不严谨也比榜单准 |
| 维度（8 个） | 长文写作 / 代码 / 结构化抽取 / 多轮工具调用 / 截图与视觉理解 / 长上下文 / 中文语感 / 指令遵循 |
| 频率 | 每周一次自动跑（成本可控：20 题 × 5 模型） |
| 输出 1：雷达图 | 每个模型在 8 维的得分 + 成本 + P50 延迟 |
| 输出 2：**能力上限标记** | 某维度所有模型都 <70% → 标红，并在立项时警告"这类目标当前不可行" |
| 输出 3：路由表 | 由得分自动生成"哪个模型做哪类步骤"，人可覆盖 |
| 输出 4：漂移预警 | 同一模型分数周环比降 >3pct → 告警（这是发现"上游悄悄降级"的唯一手段） |

**和"剔除无用环节"的联动**：先测能力上限，再决定环节去留。如果某环节所有模型都做不到 80%，那不是模型选错了，是**环节设计错了**——应该拆小、换规则、或者整段砍掉。这个顺序不能反。

### 5.2 兵工厂：三个粒度 + 一个设备池

你原来的设想是"把 WorkBuddy/Trae/Opencode 提炼成通用单条 API"。我建议**分三个粒度**，因为这三类东西的抽象难度完全不同：

| 粒度 | 抽象成什么 | 例子 | 谁来适配 |
|---|---|---|---|
| **L1 原子能力** | 一次调用 = 一个明确动作 | `image.generate`、`web.fetch`、`social.xhs.publish` | 我们写适配器（稳定） |
| **L2 会话任务** | 一次调用 = 一个多步任务，有过程 | `web.research.deep`（自己会搜索、读页、汇总） | 包一层，暴露过程事件 |
| **L3 智能体托管** | 一个持续存在的 Agent，我们只发目标和收结果 | Orca 里的 Claude Code / Codex 会话 | 只做生命周期管理，不做过程干预 |

**为什么要分**：L1 可以严格契约化、精确计费；L3 只能按"会话"计费和验收。混成一条 API 会导致要么管太死（L3 跑不动）、要么管不住（L1 计不了费）。**这是 v0.1 "一条标准 API" 说法的必要修正。**

**设备池**（你的小米/安卓/Linux、Mac mini、第三方 Agent37）：

| 类型 | 承载 | 容量单位（关键修正） | 分配策略 |
|---|---|---|---|
| 安卓真机/云手机 | App 端登录态操作、发布、互动 | **并发会话数**，不是台数 | 一设备一账号一 IP，租期自动回收 |
| Linux 容器 | 爬虫、代码执行、批处理 | 并发容器 | 按需拉起、限时回收 |
| Mac mini | iOS 生态、桌面自动化、Orca 宿主 | **并发会话**（8–12/台，需实测） | 固定归属，避免登录态抖动 |
| 第三方（Agent37 等） | 补充能力 | 按次 | 挂在 L1 或 L2，不占本地资源 |

> 容量单位统一成"并发会话"是 v0.1 的一个错误修正：按"台数"算会严重高估产能（详见 `INTEGRATION-ORCA.md` 第 6.2 节）。

### 5.3 训练与 harness 模板化（含商业化路径）

你提到"把 harness 预先封装成模板，供团队其他人或客户复用"。这句话其实藏着一条商业化路径，值得单独说：

```
训练士兵 → 沉淀 skill → 封装 harness 模板 → 自己复用（提效）
                                        └→ 教别人（课程）
                                        └→ 卖给客户（交付物）
```

**三层资产，价值递增**：

| 层级 | 形态 | 复用对象 | 变现方式 |
|---|---|---|---|
| skill | 一个 SKILL.md（触发条件/步骤/判据/反例） | 自己的 Agent | 内部提效 |
| **harness 模板** | skill + prompt + 工具配置 + eval 集 + 接口契约，**开箱能跑** | 团队、客户 | 交付项目 / 订阅 |
| 课程 | 模板 + 讲解 + 学员作业 + 验收标准 | 学员 | 知识付费 |

**关键判断**：harness 模板才是真正的产品。因为 skill 谁都能写，而"一套能跑起来、有 eval 兜底、换个环境也能用的 harness"是有壁垒的。

**训练纪律（沿用 v0.1，不变）**：没有 eval set 的 skill 不许上线；灰度 10%/3 天；季度复核，失效即下线。

### 5.4 熵减引擎（G 类目标的专用机制）

这是唯一一个"产出为负成本"的目标类型，值得单列，因为它的 ROI 最好算，也最适合作为第一个验证目标。

| 子类 | Agent 干什么 | 可计量的产出 |
|---|---|---|
| 订阅审计 | 读账单/邮件 → 找重复、未用、可降级 → 出清单 → 执行取消 | 月省 ¥X |
| 设备清理 | 盘点设备 → 挂二手/回收 → 出处置清单 | 回收 ¥Y + 释放空间 |
| 数据整理 | 去重、归档、建立索引 → 出目录结构 | 查找耗时从 A 降到 B |
| 物品清理 | 盘点 → 分类 → 处置建议 | 释放空间 + 减少维护 |
| 省钱攻略 | 比价、找替代方案、优惠叠加 | 单次省 ¥Z |

**为什么这类目标应该优先**：它同时具备"可计量、低风险、不依赖外部平台、30 天见效"四个特征，是验证整套系统最便宜的实验。

## 6. 信息架构（8 个页面，重构）

| # | 页面 | 只回答一个问题 | 关键设计 |
|---|---|---|---|
| 1 | **今日** | 今天有什么事非我不可？ | 顶部 3 个数字（决策负载/注意力余额/异常数）+ 8 条决策卡片 + 一句"今天到此为止" |
| 2 | **收件箱** | 我刚想到什么来着？ | 一句话输入，AI 三问，一键转目标或转兴趣池 |
| 3 | **目标** | 这些事值不值得继续？ | 双轨分栏（赚钱/进化），每张卡显示"预算用掉多少 + 还剩几天 + 是否触发止损" |
| 4 | **执行** | 活干到哪了，卡在哪？ | 默认只显示"异常"（卡住/失败/超预算），正常任务折叠成一行统计 |
| 5 | **团队** | 谁在干，谁该走？ | Squad 编制、Agent 绩效卡、能力标签、退役队列 |
| 6 | **兵工厂** | 现在能用什么，贵不贵？ | 中转 API 目录、设备池占用、Provider 比价、**模型雷达图** |
| 7 | **资产** | 我变强了吗？ | skill 版本、harness 模板、认知卡库、课程草稿 |
| 8 | **账本** | 值不值？ | **双币种**：钱（六分项）+ 注意力（min/outcome），同屏对照 |

**与 v0.1 的差异**：新增"收件箱"（体感入口），"成本"改为"账本"（双币种），"能力与 Provider"并入"兵工厂"（含模型雷达），"闸门"从独立页降为"今日"页的一个区块——因为闸门本质就是 L1 决策，不该单独占一个页面。

## 7. 课程：不是第 8 个模块，是系统的自验证

你把"课程"列在目标里，我建议给它一个更准确的位置：**课程是这套系统的验收测试，也是一条赚钱线。**

**三条价值同时成立**：

1. **验证**：如果这套体系讲不清，说明你自己没跑通。能教，是"跑通"的最硬证据。
2. **变现**：知识产品属于 C 类赚钱目标，收入反哺系统成本，形成自举。
3. **沉淀**：写课的过程会暴露 skill 里的隐含知识（tacit knowledge），这些恰恰是 harness 模板最值钱的部分。

**但不要现在做。** 判断标准是：**当你自己用这套系统连续 8 周、且至少 3 个目标达标之后**，再动笔。否则你会在还没验证的体系上写教程，最后既要改系统又要改课，两头崩。

**课程形态建议**：不做录播课，做**"可运行的模板包 + 讲解"**。学员拿到的是能直接跑起来的 harness，而不是一堆 PPT。这才是和你这套东西匹配的产品形态，也避免和泛滥的"AI 课程"同质化。

## 8. MVP 重排（这是本稿最关键的一个判断）

v0.1 说第一周做"任务状态机 + 租约回收"。**这个顺序要改。** 理由：你的第一约束是带宽，不是并发。如果第一版验证的是"调度器稳不稳"，你会在第 4 周做出一个技术上正确、但你不想打开的系统。

新的顺序是：**先验证"你愿不愿意用"，再验证"Agent 干得好不好"，最后才验证"规模撑不撑得住"。**

| 阶段 | 周期 | 做什么 | 明确不做 | 毕业标准（达不到就停，不硬推） |
|---|---|---|---|---|
| **P0 带宽闭环** | 2 周 | 收件箱 + 双轨目标卡 + 今日页 + 手动执行（你自己干，Agent 不接活） | 调度器、租约、多 Agent | 连续 7 天每天用它看完板并立项，日均 ≤10 分钟，产出 ≥3 个可验收目标 |
| **P1 单兵闭环** | 2–3 周 | 接 1 个 Worker + L1 质检 + 双币种账本 + 模型雷达（跑第一版） | Squad、抢模式、多 Provider | 1 个熵减目标跑完，**省下的钱 > 系统当月成本** |
| **P2 小队闭环** | 4 周 | Squad 编制 + 工作流模板 + 认知卡 + harness 模板 v1 | 500 规模、多域管理 | 3 个目标并行，日决策 ≤12，返工率 ≤20% |
| **P3 规模** | 6–8 周 | 调度器（租约/幂等/分片）+ 多设备池 + Orca L2 绑定 | 课程 | 150 个 Agent，决策负载不上升（这是唯一硬指标） |
| **P4 外化** | 按需 | 课程 + 客户交付 | — | 3 个外部用户能独立跑通 P1 |

**P0 的毕业标准里有一条是刻意设置的**：`日均 ≤10 分钟`。如果做不到，说明这个产品对你是负担，后面所有投入都会沉没。**先花 2 周证明它值得存在，再花 8 周把它做出来。**

## 9. 双币种单位经济

### 9.1 钱

沿用 v0.1 的六分项，但按当前阶段调整量级：

| 分项 | P1（1 条线，≈10 Agent） | P3（150 Agent） |
|---|---|---|
| 模型 | ¥800/月 | ¥2.0 万/月 |
| 工具订阅 | ¥300/月 | ¥0.6 万/月 |
| 设备 | ¥0（先用本机） | ¥1.2 万/月 |
| 返工 | +25% | +25% |
| 质检 | +10% | +12% |
| 人力 | 你自己的时间（见 9.2） | ¥9–12 万/月 |

### 9.2 注意力（新）

| 指标 | P0 目标 | P3 目标 |
|---|---|---|
| 日决策数 | ≤10 | ≤15（**不随 Agent 数量增长**） |
| 信息压缩比 | 不适用（全手动） | ≥30:1 |
| min/outcome | ≤20 min | ≤8 min |
| 决策疲劳事件（否决率异常） | 0 | ≤1 次/月 |

> **P3 的唯一硬指标是"决策负载不上升"**。如果 Agent 从 10 个涨到 150 个，你的日决策从 10 涨到 30，那这套系统只是把工作搬到了你身上，规模化的意义为零。

## 10. 与 Orca 的关系（沿用 `INTEGRATION-ORCA.md`，摘要）

| 项 | 结论 |
|---|---|
| 定位 | Orca = 执行面（手与眼睛），我们 = 控制面（脑与账本） |
| 绑定深度 | **L2 会话级**（L1 任务级 → L2 → L3 暂缓） |
| 核心机制 | 会话即租约、worktree 即任务载体、hook 即心跳、transcript 即 trace、snapshot 断点续跑 |
| 接口 | Adapter 六个原子动作：probe/spawn/send/steer/harvest/kill |
| 三条必改 | ① 订阅制下 CPO 改"订阅摊销+配额+复核分钟"；② 容量单位改并发会话；③ 订阅条款是红线 |
| 意外收益 | coding 任务有真 oracle（测试/PR），**抢模式在这里成立** |

## 11. 风险清单

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| **产品变成"又一个待办清单"** | **高** | **极高** | P0 阶段用"日均 ≤10 分钟"作为硬门槛，达不到就砍功能，不加功能 |
| 体感目标大量烂在收件箱 | 高 | 中 | 14 天自动归档为兴趣，不催办；催办会让人不想再记 |
| 进化目标侵占赚钱目标的时间 | 高 | 高 | 双轨各有独立时间预算，超支时赚钱轨优先 |
| 决策疲劳导致批量误批 | 中 | 高 | 否决率异常检测 + 深夜禁做 L0 |
| 平台限流/封号 | 高 | 极高 | 备用承接账号 + 健康分降频 + 合规规则库 + AI 标识硬拦截 |
| 订阅条款/账号风险（Orca 场景） | 中 | 极高 | 单账号单并发；>20 Agent 转 API 计费 |
| 模型能力被高估，立了做不到的目标 | 中 | 高 | 模型雷达的"能力上限标记"，立项时强制校验 |
| 课程在体系未验证时开写 | 中 | 中 | 8 周 + 3 个目标达标后才动笔 |

**三条红线**：① 高风险动作未经人审不执行；② 不为规避 AI 标识做后处理；③ 死信任务不静默丢弃。
