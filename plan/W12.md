## 1. 评估范围与方法

**范围**：`docs/` 全部（PRODUCT-DESIGN v0.1/v0.2、TECH-ARCHITECTURE-v1、DEV-PLAN-v1、
INPUT-CHANNELS-v1、INTEGRATION-ORCA、MERGE-REVIEW-v1、agent-fleet-review-2026-10-18）
+ `plan/` 全部（W01–W11、windows.yaml、boundaries.yaml）+ 仓库实际状态
（`deploy/`、`scripts/`、`backend/app/modules/`、`.env.example` 均已核对）。

**三条评估标准**：

| 标准 | 判据 |
|---|---|
| 实用性 | 不做这件事，系统会**具体坏在哪**（拒绝「理论上更好」） |
| 契合度 | 能否挂进现有窗口与契约，不新造平行体系 |
| 贡献度 | 对 P0–P4 哪个毕业标准有贡献，且贡献可度量 |

**缺口是怎么找到的**（五类来源，每项提案均注明出处）：

1. 上游文档设计了，但 60 个 issue 无一落地（如 Legion 的 Debrief、KPI 回流）；
2. 文档**假设它存在**，但没有任何窗口拥有它（`LITELLM_BASE_URL`、「外部 cron」、`deploy/` 根目录）；
3. 毕业标准依赖它，但没有度量手段（P0 的「日均 ≤10 分钟」）；
4. 风险清单挂了号，但没有实现窗口（AI 标识、提示注入、账号健康分）；
5. 核心链条上的断点（体感 → 目标 → **?** → 任务 → 执行 → 验收 → 账本）。

**结论先行**：发现 **13 项值得加入**——其中 3 项是「人人都假设它存在、但没有窗口做它」的
无主基础设施，建议 **Wave 1 开工前决断**；13 项合计约 20 人日，不到一个窗口一周的产能，
但每一项都对应一个「系统会具体坏在哪」的点，而不是装饰性功能。

## 3. 第一类：无主基础设施（建议 Wave 1 前决断）

这一类三个的共同点：**文档里已经写了它们存在，60 个 issue 里没有任何一个负责让它们存在**。
并行开发里，这类缺口的危险不是「慢」，是第 3 周有 5 个窗口同时发现「我以为有人做了」。

### 3.1 模型网关落地：LiteLLM 部署与 Provider 渠道管理

| 项 | 内容 |
|---|---|
| 用途 | 把架构选型的 LiteLLM（TECH-ARCHITECTURE §2.1，61.5k star）真正跑起来：compose 服务 + Provider 渠道表（渠道 = 供应商 + 接入方式 + 账号池 + 权重/优先级 + 熔断状态）+ 路由与 failover + 逐请求计量回写账本（W07「模型」分项） |
| 加入理由 | **三个窗口已经假设 `LITELLM_BASE_URL` 存在，但没有任何窗口部署它**：W02-I02（三问，Wave 2）、W08（题库运行框架，Wave 1 就要 fake provider 之外的出路）、W11-I05（截图 OCR）都写明「走 LITELLM_BASE_URL，不直连厂商」；`.env.example` 第 39 行有占位符，`deploy/docker-compose.yml` 里**没有 LiteLLM 服务**（已核对：只有 db/redis/migrate/api/web/caddy）。这是全部 AI 功能的唯一 choke point——缺了它，Wave 2 起要么逐个窗口阻塞，要么每个窗口自己写 Provider 适配（正是架构文档要避免的重复造轮子） |
| 预期效果 | ① Provider 差异、key 轮换、failover 收敛到一处，换模型不改业务代码；② 每次 LLM 调用天然带渠道/模型/成本三元组，W07 账本「模型」分项有真实数据源；③ 配额消耗率（W07-I05）有采集点 |
| 落地建议 | 部署并入 #3 的运维包（compose 加一个服务）；渠道/路由数据模型放 W08 的 `evals` 模块（兵工厂的「中转 API 目录」半边，PRODUCT-DESIGN §6 页面 6），**不新增第 11 个模块**，避免 router.py 二次变更。约 3 人日。Wave 1 内 |
| 主要风险 | LiteLLM 自身升级/配置漂移——用固定镜像 tag + 配置入库（不在容器里手改）；渠道 key 只进 `.env`/secret，不进库 |

### 3.2 定时作业调度器（内部 cron）

| 项 | 内容 |
|---|---|
| 用途 | 一张 `jobs` 表 + 一个执行器：统一注册、并发上限、错过补跑、执行留痕、失败告警。**复用 W03 的队列与租约语义**（作业即一种任务 kind），不自建第二套调度 |
| 加入理由 | 现有规划里**至少 7 处假设「外部 cron」存在，但 cron 本身无主、无监控**：W02-I05 `archive_stale_intake.py`、W03-I02 `reclaim_leases.py`、W04-I03 `sweep_devices.py`、W08-I04 `check_drift.py`、W11-I03 `daily_digest.py`、W11-I06 `journal_review.py`、W11 提案的 T+N 对账。单机上「外部 cron」可以是 crontab，但**谁保证它跑了、失败谁知道、错过了补不补**没有答案——脚本静默失败的后果是：止损永不触发（规则存在但没人检查）、归档从不执行、漂移预警不发。另外 W04-I04 的「告警表」、W08-I04 的「告警条目」、W10-I02 的「异常数」三个来源目前**没有统一读者** |
| 预期效果 | ① 后台作业从「写了没人跑」变成「跑了可见、失败有告警」；② 「异常数」有确定口径（W10 今日页直接可用）；③ 缺席窗口（W11-I01）的批处理派活有调度底座 |
| 落地建议 | W03 追加 issue（`modules/tasks/` 内加 job kind + `scripts/job_runner.py`），失败写 alerts 表；与 W11-I03 通知中心对接（未纳入 W11 前先落库）。约 2–3 人日。Wave 2 前（W03-I02 的回收脚本第一个需要） |
| 主要风险 | 作业重复执行——用 W03 既有租约 + 幂等键，不新机制；执行器本身要能被 sweep（自己也是 job） |

### 3.3 部署流水线 + 备份 + 恢复演练

## 4. 第二类：核心链条断点（体感 → 目标 → **?** → 任务 → 执行 → 验收 → 账本）

产品的核心链条上，**「目标变任务」这一环没有 issue**。W02 产目标卡，W03 产任务，
中间隔着一个没人负责的转换器。这是「用 500 个 Agent 放大一个人」与「一个人手工派活」
的分界线。

### 4.1 目标 → 任务 AI 拆解

| 项 | 内容 |
|---|---|
| 用途 | 目标卡（+ 模板默认值）→ S 档模型生成任务树（mission → task，每节点带 `requires` / 预算 / 验收命令）→ **人工增删改后入队**。Legion 设计 M2「目标拆解：由指挥档模型把目标拆成任务树，人工可增删改」 |
| 加入理由 | ① 链条断点：P1 毕业标准「1 个熵减目标跑完」，而熵减引擎（PRODUCT-DESIGN §5.4）的订阅审计 = 读账单 → 交叉比对 → 生成清单 → 执行取消，**这四个任务目前只能手工建**；P0「手动执行」是刻意设计，但 P1 起每个任务都手工建，「放大带宽」就不成立。② 有模板地基：W02-I04 模板库已给「默认三问答案」，任务树是同一模式的自然延伸（模板给默认拆解，AI 按体感微调） |
| 预期效果 | ① 目标卡一键产出任务树，派活（W03）有源头活水；② 人工只做「删/改/批」，不做「从零想」——把 L0 决策从「设计任务」压缩成「审阅任务」；③ 与 W08-I03 能力上限校验联动：拆解时就知道哪类节点当前不可行 |
| 落地建议 | W02 追加 issue：`POST /goals/{id}/decompose`（走 #1 网关，幂等）；产物是 **draft 任务树**，人确认后调 `tasks.service` 公开函数入队（跨模块合法路径①）。约 2 人日。Wave 2 末 / Wave 3 |
| 主要风险 | AI 直接建高危任务——拆解结果一律 draft，入队必须过人审或模板白名单；失败时返回 502，不返回编造的任务树（同 W02-I02 纪律） |

### 4.2 目标 KPI 回流（最小版：北极星填报）

| 项 | 内容 |
|---|---|
| 用途 | 赚钱轨北极星指标（模板 A = 有效线索数、模板 B = 回款额）≤30 秒填报 + 自动聚合进目标看板与止损判定；自动采集（平台数据接口）留 P2 后 |
| 加入理由 | **三个关键机制都依赖 KPI 数据，而采集入口不存在**：① W02-I04 止损判定（产出 < 历史 P25 → 冻结）没有「产出」数据可判；② W07-I02 达标产出（CPO 分母 = T+7 达标产出）没有达标判据；③ W02-I06 目标看板只有「预算/天数/止损」三项，没有「干到哪了」。Legion M2 的「KPI 回流：手动填报 + 自动采集」在 10 窗口里零落地 |
| 预期效果 | ① 目标「值不值得继续」第一次有数据可依，不凭体感；② 止损从「规则存在」变成「规则被触发」（与 W11 提案的 W02-I08 T+N 对账合并设计）；③ P2 内容引流上线时，自动采集有填报口径可对齐 |
| 落地建议 | W02 追加 issue：`POST /goals/{id}/kpi`（一行：指标值 + 口径备注）+ `GET /goals/{id}/kpi`（时序）；与 W02-I08 合并为一个 issue（KPI 是止损/复用回看的数据源）。约 1 人日（最小版）。Wave 3 |
| 主要风险 | 填报造假/漏报——只做最小集（一个数字 + 一句话），不做复杂表单；漏报不催办（同 Inbox 纪律） |

### 4.3 目标复盘（Debrief）自动生成

| 项 | 内容 |
|---|---|
| 用途 | 目标进入终态（achieved / frozen / degraded）时自动生成结构化复盘：KPI 实际 vs 目标、成本（双币种）、成败归因、可复用经验 → 直接产出认知卡草稿（W08-I06）与课程素材（P4） |
| 加入理由 | Legion M6 有「每个 goal 结束自动生成复盘」；v0.2 §7 把课程定位为「系统的自验证」；但 10 窗口 + W11 里**没有复盘**。认知进化轨的链条是「输入 → 认知卡 → 复用」，终点是「这次做对了/做错了什么」——没有 Debrief，W08-I06 的卡只能手工建，「沉淀」是口号；P4 课程也没有原料 |
| 预期效果 | ① 每个目标结束沉淀 1 份复盘 + N 张卡草稿，认知资产有稳定来源；② 复盘数据反哺模板库（哪个模板的默认拆解更准）；③ P4「3 个外部用户跑通 P1」的课程素材自动积累 |
| 落地建议 | W02 追加 issue：监听目标终态 → 生成复盘（LLM 走 #1 网关，纯函数组装 + 模型成文）→ 调 `evals.service` 建卡草稿。约 1.5 人日。Wave 4 |
| 主要风险 | 复盘变成流水账——结构固定为「目标/实际/差异/归因/下一步」五段，超长即失败；归因只用「可能原因」（同 W11-I06 措辞红线） |

## 5. 第三类：资产面与数据治理缺口

### 5.1 认知卡检索与冲突消解

| 项 | 内容 |
|---|---|
| 用途 | ① 三段检索：触发条件硬过滤（平台/类目/形态）→ 向量语义召回 → 置信度 × 新鲜度排序；② 冲突消解：新卡上线必须声明「覆盖/废止哪张旧卡」，形成版本树，**同触发条件不允许两张有效卡并存**；③ 失效期到期自动转「待复核」，一年未复核归档 |
| 加入理由 | agent-fleet-review #13（P1）明确指出：「认知卡只有字段，没有存哪、怎么被找到、冲突算谁的——有字段没有检索，卡库会烂掉」。W08-I06 当前只定义了字段与 `reuse_count > 0`，**检索、覆盖关系、自动复核全无**。几百张卡之后，「这次该用哪几张卡」是真难点；没有冲突消解，Agent 会随机漂移，且你永远不知道是能力退化还是卡打架 |
| 预期效果 | ① 卡库可复用、可追溯，真正「越干越强」；② 复用计数从虚荣指标变成有效指标（带 holdout 记录）；③ 「失效即下线」的 skill 纪律（v0.2 §5.3）有卡级对应物 |
| 落地建议 | W08 追加 issue：迁移里**早期定 schema**（`supersedes_id`、trigger 硬过滤字段、embedding 引用、`review_due_at`）——W08-I06 建表时就要留，否则 P2 返工改表；检索实现约 1.5–2 人日（embedding 走 #1 网关）。Wave 3 定 schema，Wave 4 实现 |
| 主要风险 | 向量检索召回差——硬过滤先行（review 估计能砍 80% 噪声），语义只做精排 |

| 加入理由 | PRODUCT-DESIGN §5.1 的输出 3 就是路由表，W11 也已提 W08-I07，但 W08-I02/I03 只做到「出雷达图 + 能力上限标记」。雷达到「直接省钱」之间缺最后一公里：不生成路由，雷达就只是周报 |

## 10. 建议纳入顺序与两个决策点

**决策点 1（Wave 1 开工前，本周内）**：#1 模型网关 + #3 部署运维包 + #2 作业调度器。
理由：#1 是 Wave 1（W08-I01）之后所有 LLM 调用的前提，#2 从 Wave 2（reclaim_leases）起
就需要主人，#3 决定 T0 能否验收。三项都是「无主基础设施」，越晚决断，越多窗口会
「以为有人做了」而各自开工。同周启动 ICP 备案。

**决策点 2（Wave 3 边界）**：#4 拆解 + #5 KPI + #6 使用度量 + #7 注入防护。
理由：这四项决定 P1 能否毕业——「单兵闭环」需要目标→任务的源头（#4）、达标的数据（#5）、
毕业标准的度量（#6），以及无人值守的安全前提（#7）。

**P2 波次**：按「模板 A 内容引流上线」的顺序排——#10 合规与 #11 账号资产必须在上线前，
#8 卡检索 / #9 路由表 / #12 Debrief 紧随其后，#13 保留策略在 P3 前完成。

**产能账**：13 项合计约 20 人日 + W11 的 7 个 issue 与 10 个追加 issue——这就是
「W11 + W12 作为一个 Wave 5+ 的候补波次」的合理规模：不挤占 W01–W10 的四个波次，
但也不应该无限期推迟（#1/#2/#3 尤其不能）。
